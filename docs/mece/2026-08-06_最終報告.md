而 Superpowers、planning-with-files、C.A.S.E.、MECE-Autopilot 全都裝著沒用上。

## 核心洞察

**一、真正的原因是可達性,不是行為。**

實測 dump 出 Pi 送出的 prompt:**43 個技能有描述,122 個只有名字。** `case-framework`、
`planning-with-files`、README 畫的整個 Layer 1(`grilling-protocol` / `contrarian-review` /
`adversary-review`)、`hello-reflect`、`loopy`、`workflow-os-guide`,以及 README 招牌的
13 個蒸餾技能 —— **全在沒有描述的那 122 個裡。**

模型不是不用方法論,是**看不到方法論**。

**二、你要的機制整套已經存在,是你自己寫的。**

C.A.S.E. 的 `02_Task_Queue/Task_NNN/` 有 `status.txt` 狀態機、`role.md`、`recipe.md` +
本地 DoD、`planning.md`、`output.md`、`feedback.md`、`action_log.jsonl`、Worker-Checker
雙軌、3 次自癒上限、驗證器、bootstrap 腳本。需求逐條對得上,**一項不缺**。

它從未動過的原因是三個條件互鎖:skill 在 catalog(無描述)→ 模型不知道 → 沒人跑
`bootstrap.py` → cwd 不是 CASE 專案 → `case-bridge` 與 `AGENTS.md` 都不注入協定。
**沒有任何一步會自己發生。**

**三、「bridge 有問題」不成立,但「通道」有問題。**

| 機制 | 通道 | 實測 |
|---|---|---|
| skill 裡的 Source 欄 | skill 文字 | 3/3 被跳過 |
| task-shape 路由字條 | `systemPrompt` | 送到了,37 次搜尋照跑 |
| 引用閘 | `tool_call` → `{block, reason}` | 3/3 開火,檔案內網址 0→10/15 |

三個都是 bridge。差別是建議 vs 拒絕。

**四、MECE-Autopilot 是「可見還不夠」的反證。**

它 core 有描述、bridge 注入完整 orchestrator 指令 —— **佈線滿分,仍未觀察到自主啟動。**

**五、CASE 的驗證器是偽收斂製造機。**

15 條檢查只有 5 條會失敗。沒有稽核軌跡、沒有驗收標準、沒有計畫、`output.md` 一個字,
都能拿到 `✅ VERIFICATION PASSED`。而 MECE-Autopilot 的收斂閘門明文禁止偽收斂。

## 妥協與 Trade-offs

1. **不重寫 CASE / MECE 為原生** —— 分叉風險。本 repo 有 `reference/oh-my-pi` 凍結分叉
   害它「找到」不存在缺陷的疤。
2. **`--strict` 是 opt-in** —— 直接升 errors 會弄壞所有現存使用者的既有任務。
3. **B2 仍是建議通道** —— 依 MECE 的反證有很大機率不會自己發生。便宜,先做先量。
4. **B5 可能永遠不做** —— 這一輪已為「先蓋再量」付過兩次代價。

## 本輪流程本身的收穫

**盤點在設計之前。** R1–R4 四輪討論收斂出的機制整套已經存在。擁有者一句
「先把目前專案提到的機制都真的了解」省下的,正是重造整套 task queue 的時間。

**推論了四次才去看實際的 prompt。** 查設定檔、查安裝目錄、查三個技能根目錄 ——
中間一度準備報告「9 個核心技能不存在」這個錯誤結論。`PI_HARNESS_DUMP_PROMPT`
寫在 CLAUDE.md 裡,用了 30 秒就有答案。

**把選擇丟給使用者不是中立。** 我曾把兩個選項丟給擁有者選,他按了暫停:「我看不懂,
亂選又會讓你目標偏移」。而 MECE-Autopilot 的協定裡就寫著「**預設主動,顯式否決**」——
面板決策,使用者保留否決權。這一條我違反了,他用他自己寫的規則糾正我。
