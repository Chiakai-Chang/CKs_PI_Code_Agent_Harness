## 1. 結論先講

**MECE 面板第四輪收斂出來要「新建」的那套機制,整套已經存在,而且是擁有者自己寫的。**

它沒有被啟動的原因不是缺少程式碼,是**它在 system prompt 裡沒有描述**,加上**兩個條件式互鎖**。

## 2. C.A.S.E. 已經有完整的 task queue 協定

`external/Local-Agent-Workspace/SKILL.md` 定義:

```
02_Task_Queue/Task_<NNN>_<slug>/
    status.txt        PENDING | IN_PROGRESS | REVIEW | DONE | ESCALATED
    role.md           這個任務專屬的 system prompt override
    recipe.md         步驟 + 本地 Definition of Done
    planning.md       微觀計畫(BDD scenarios)
    inputs/           輸入或前一個任務的產出連結
    output.md         主要交付物
    feedback.md       只由 Checker 或人類寫入
    action_log.jsonl  每一次工具執行的稽核軌跡
```

加上:
- **Worker-Checker 雙軌**:Worker 做完轉 `REVIEW`,Checker 驗過才 `DONE`
- **3 次自癒上限**,超過轉 `ESCALATED`
- **驗證器**:`verifiers/verify.py` / `verify.js`,檢查任務包完整性
- **bootstrap**:`scripts/bootstrap.py .` 一鍵在專案裡建立整套骨架

對照擁有者的需求原文:

| 需求 | CASE 裡對應的東西 |
|---|---|
| 每次專注做一件事 | 一個 `Task_NNN` 資料夾,`status.txt = IN_PROGRESS` |
| 做完復盤 | `output.md` + `feedback.md` + `REVIEW` 狀態 |
| 有發現就增加 task queue | 新增 `Task_NNN` 資料夾 |
| 有憑有據 | `action_log.jsonl` |
| 不要一輪做完 | 狀態機本身就不允許 |

**一項不缺。**

## 3. 為什麼它從來沒動過 —— 三個獨立原因

### 3a. `case-framework` 在 catalog 層,沒有描述

實測 prompt(40,782 字元):

```
<available_skills>  43 個技能,每個有 name + description + location
[Skill Catalog]     122 個技能,只有名字,描述不展開
```

`case-framework` 在後者。模型看得到「有個東西叫 case-framework」,看不到它是什麼、什麼時候該用。

### 3b. `case-bridge` 只在已經是 CASE 專案時才注入協定

`pi-extensions/case-bridge/index.ts`:

```ts
function isCaseProject(cwd) {
  return fileExists(cwd, "CASE.md") || fileExists(cwd, "00_Constitution");
}
```

不是 CASE 專案 → 只注入一行「framework is active in this harness」加兩個腳本路徑。實測 prompt 裡就是這一行。

### 3c. `pi-rules/AGENTS.md` 的路由規則同樣是條件式

`AGENTS.md:93`:

> 有邊界的多任務專案／**cwd 有 `CASE.md` 或 `00_Constitution`** → `case-framework`

### 互鎖

```
協定要生效  →  需要 cwd 是 CASE 專案
cwd 要變成 CASE 專案  →  需要有人跑 bootstrap.py
有人要跑 bootstrap.py  →  需要模型知道 CASE 存在且該用
模型要知道  →  需要 case-framework 有描述在 prompt 裡
                                    ↑ 它在 catalog,沒有描述
```

**沒有任何一步會自己發生。**

## 7. 這改變了設計方向

MECE 第四輪的收斂結論是「註冊 queue 工具、擋項目邊界」。**那是重造一個已經存在的東西。**

修正後的方向應該是:**讓既有的 CASE 協定能被到達**,而不是新建平行機制。三個互鎖點各有對應的解法方向:

1. `case-framework` 需要從 catalog 升到 core(有描述)
2. `case-bridge` 的 `isCaseProject` 互鎖需要有一條「尚未 bootstrap 時怎麼辦」的路徑
3. 外來的 19 個技能佔著描述層 —— 這是本 harness 管不到的部分,但可以在自己的路由裡指名

**先盤點再設計,省下的正是重造整套 task queue 的時間。**
