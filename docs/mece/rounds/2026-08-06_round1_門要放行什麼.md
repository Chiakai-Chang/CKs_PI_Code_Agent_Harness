# Round 1:這個門到底要放行什麼

**日期**: 2026-08-06
**問題等級**: L2
**問題**: 多交付物請求的前置門控,武裝條件、放行條件、未達成時的反應各該是什麼?

## MECE 維度分解

| 維度 | 內容 | 互斥性檢查 |
|---|---|---|
| D1 需求真實性 | 這個門有沒有真的解決「沒先規劃就開始」 | 只問「對不對題」 |
| D2 誤判與韌性 | 誤擋代價、卡死風險、退場 | 只問「壞掉會怎樣」 |
| D3 成本與延遲 | token、輪次、牆鐘時間 | 只問「多少錢」 |
| D4 操作體感 | 擁有者每天的感受 | 只問「用起來如何」 |
| D5 可稽核性 | 事後查得到嗎 | 只問「留下什麼」 |

覆蓋檢查:五個維度合起來涵蓋「對不對題 / 壞掉 / 成本 / 感受 / 證據」,無明顯遺漏。

**🎭 老陳:**

先把能做和不能做講清楚,不然後面全是空話。

`ToolCallEventResult` 只有 `{ block?, reason? }`,`types.d.ts:778`。所以「未達成時的反應」實際上只有兩種:擋、或不擋。沒有「降級」這種東西 —— 想降級只能自己在 handler 裡數次數。

但我剛查到一件被忽略的事:`ExtensionUIContext` 有 `select()`、`confirm()`、`input()`,全部回 `Promise`,而 `tool_call` handler 本身是 `async`。**意思是門可以在決定擋不擋之前,真的跳一個對話框問人,等他回答。**

`ctx.hasUI` 的文件寫「whether dialog-capable UI is available (true in TUI and RPC modes)」。所以 `--print` 下要走別條路。

## 本輪新發現

1. **`ctx.ui.select/confirm/input` 存在且可在 `tool_call` 中 await** —— 之前的選項空間漏了一整類。
2. **但「叫模型問問題」在本機已有實測反證** —— 一輪燒在問四個問題上;ClarQ-LLM 說連 SOTA 也只有 50–60%。
3. **老魔的根本挑戰:真實 session 的請求並不模糊。** 需求釐清可能根本不是缺口。
4. **CK 點出一個被混淆的區分**:harness 問「你的需求是什麼」(有價值)vs harness 問「我該怎麼設計」(轉嫁風險)。

## 結論

「放行條件 = 載入釐清技能」(原選項 B)在本輪即出局:它把「使用率」變成通關條件,CK 明令禁止的形狀。

「放行條件 = 對話框問使用者」尚未出局,但已被兩個實測反證夾擊。
