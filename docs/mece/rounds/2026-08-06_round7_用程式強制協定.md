**🎭 老韓:**

那我來回答 CK 真正的問題:**狀態機能不能用程式強制?**

我看了 CASE 的定義。它的轉換規則是這樣:

```
PENDING     → IN_PROGRESS  (Worker 開始)
IN_PROGRESS → REVIEW       (Worker 提交)
IN_PROGRESS → ESCALATED    (前置條件缺口)
REVIEW      → DONE         (Checker 核可)
REVIEW      → PENDING      (Checker 退回,重試 < 3)
REVIEW      → ESCALATED    (重試 >= 3)
```

**每一個轉換都是一次對 `status.txt` 的寫入。** 而寫入是 `tool_call`。

意思是:**這個狀態機的每一步,harness 都能在它發生之前看到,而且能擋。**

具體可判定的清單:

| 規則 | 怎麼判定 | 協定出處 |
|---|---|---|
| 非法轉換(`PENDING` 直接跳 `DONE`) | 讀舊值、比對新值 | §4 轉換規則 |
| 同時兩個 `IN_PROGRESS` | 掃 queue 目錄 | 「一次一件」 |
| Worker 自我核可 | 同一 session 先寫 `IN_PROGRESS` 再寫 `DONE` | §1 雙軌驗證 |
| `DONE` 前沒有 `retro.md` | 檔案存在性 | §13a |
| 寫到自己任務目錄之外 | 路徑比對 | §5 權限邊界 |
| `REVIEW→DONE` 沒過驗證器 | 跑 `verify.py --strict` | 新增的 A1 |

**六條,全部在 `tool_call` 上可判定,全部不需要模型配合。**

## 本輪新發現

1. **「用程式提醒」一直有在做,「用程式強制」從來沒有。** 13 個 bridge 裡,方法論相關的
   `tool_call` block 數量是 **0**。
2. **CASE 的狀態機每一步都是對 `status.txt` 的寫入** —— 也就是每一步都是 `tool_call`,
   harness 在它發生前看得到,而且擋得住。
3. **六條可判定的規則**,全部不需模型配合(非法轉換、兩個 IN_PROGRESS、自我核可、
   DONE 前無 retro、越界寫入、REVIEW→DONE 未過驗證器)。
4. **程式管得了「怎麼做」,管不了「要不要開始做」。** 轉換可判定,決策不可判定。
   這解釋了為什麼 B1 是 0/3 —— 那是決策問題,不是轉換問題。
5. **作用域不重疊就沒有順序問題** —— 這六條只管 `02_Task_Queue/` 內的寫入,與既有守衛正交。
6. **協定散文與強制程式會漂移**(上游剛用 §13a 示範過),需要測試綁住並標明上游是唯一真相。

## 結論

CK 的直覺成立,但要切成兩半:

* **遵循(可程式化)** —— 六條 `tool_call` 守衛 + harness 自寫稽核軌跡。
* **啟動(不可程式化)** —— 需要一個確定性的人為入口。`/browse` 是這個 repo 已有的先例。
