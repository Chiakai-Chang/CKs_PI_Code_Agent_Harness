# Round 4:SWOT + TOWS 與收斂

**日期**: 2026-08-06
**問題等級**: L2

## SWOT(彙整四輪)

### Strengths(本 harness 已有的)

- `tool_call` 的 `{block, reason}` 是唯一被實測證明能改變行為的通道(引用閘:檔案內網址 0/0/0 → 10/15/0)
- 退場機制已存在且測過(`refuse()`:擋滿 3 次退場,計數在嘗試而非結果)
- 量測儀器現在會記錄機制,不只分數
- `registerTool()` 可用,工具是模型熟悉的介面
- `ctx.ui.select/confirm/input` 可在 `tool_call` 中 await

### Weaknesses(本 harness 的)

- **沒有「即將作答」事件**;`turn_end` 無回傳型別 → 擋不到「一輪收掉整件事」
- `pi --print` 單輪 → 任何多輪或互動機制**永久無法自動驗證**
- 本地弱模型指令遵循差;寫在 skill 裡的文字實測被跳過 3/3
- 證據基礎 n=1

### Opportunities

- Routine 論文:把流程變成可執行腳本,Qwen3-14B 32.6% → 83.3%
- `clarify_task` / `queue_advance` 這類工具的**參數**是可稽核的內容證據,而不是「載入了某檔案」的代理指標
- 「有沒有真的填」是純函式可判定的,可以寫測試
- 工具參數可以直接落檔成 queue,一個動作同時滿足切分與產出

### Threats

- **敷衍**:實測有證 —— 引用閘讓編造從 0 變 4;長度下限被小塊寫入繞過
- **過度規劃**:Learning When to Plan —— 總是規劃在長任務上降低表現;簡單任務付不成比例的成本
- **GateGuard 的疤**:沒人跑過的閘上線,擋掉每個 session 的第一條 bash
- **小周**:開源使用者被擋而看不懂
- CK 的原則衝突:要 Layer 1,但不要衝高使用率、不要被無意義打斷

## 收斂決策

**放棄的:**

| 方案 | 出局理由 |
|---|---|
| A. 有 `task_plan.md` 就放行 | **實測否證** —— 三個探針 run 都寫了 plan,都還是一輪做完 |
| B. 載入釐清技能才放行 | 把使用率當通關條件,CK 明令禁止的形狀 |
| C. 對話框問使用者 | 永久無法自動驗證 + 本機已實測「一輪燒在問四個問題上」+ CK 剛表明不想被丟選擇 |
| D. 一律武裝 | Learning When to Plan 直接反對;簡單問題付不成比例成本 |

**採用的(WO-1 + SO-1 + ST-2 + WT-1):**

節拍點不在「第一個搜尋前」,在**項目邊界**。

```
D1 武裝    請求被分類為多交付物(沿用既有 classifyRequest)
           簡單請求完全不武裝 —— 預設安靜

D2 機制    註冊 queue 工具,參數承載切分內容
           放行條件 = 結構可判定(非空、項目數 ≥2、項目互異),不判斷品質

D3 攔截點  上一項未收掉就要開下一項 → block
           不是「第一個搜尋前」—— 那個點實測沒用

D4 退場    沿用 refuse():擋滿 3 次本 session 退場,計數在嘗試
D5 訊息    中文、說明原因、附關閉方式(小周維度)
D6 稽核    儀器記錄工具呼叫次數,進 baseline 的 runs 欄位
```

## 妥協與 Trade-offs(明列)

1. **接受「永久無法自動驗證」。** 這是多輪機制的本質,不是缺陷。緩解:儀器記錄呼叫次數,讓 CK 的真實 session 事後查得到。
2. **接受 n=1。** 因此預設安靜,只做「發生時接得住」。
3. **放棄擋「一輪收掉整件事」。** Pi 沒有那個事件。改擋項目邊界是次佳解,誠實記錄這是妥協。
4. **不判斷內容品質。** 只判斷結構。品質判斷會製造新的敷衍面。
