**🎭 Vera(先放最新事實):**

`019fd702` 那一輪看起來很好 —— 載入 planning-with-files、寫了七個檔案、phase 檔各 4000+ 字元。

**但第一則使用者訊息是 57,703 字元,內含 `investigation-brief`、`Phase`、`出口條件`、`反面證據`。
第三則又貼了 46,857 字元的 ACH 方法論。**

**那一輪的方法論是 CK 手動貼進去的,不是 harness 給的。** harness 的貢獻是三個閘正確地沒開火。

**🎭 老方:**

那我可以直接命名這個問題。你們一直在做的是文獻上說的 **agent-proposed activation** ——
把技能攤在模型面前,期待它提議使用。實測 0/3 不是意外,那個模式的成功率本來就不穩。

2026 的共識是另一種:**policy-mediated activation —— 系統依設定與觸發條件決定要不要啟用。**
Anthropic 的說法更直接:**deterministic backbone orchestrates the flow, with LLM intelligence
deployed only at specific steps.**

**流程持有控制權,模型只填步驟。**

**🎭 老魔:**

聽起來很美。**但 Pi 沒有 backbone。** 它的迴圈是「使用者說一句、模型跑一輪」。你要把流程放哪?

**🎭 老陳:**

有,而且這個 repo 已經在用。`pi.sendMessage(..., { deliverAs: "followUp", triggerTurn: true })`
—— **harness 主動塞一則訊息並觸發下一輪。**

`async-exec-bridge` 就是靠這個:背景工作做完,bridge 喚醒 agent 帶回結果。剛加的
compaction-echo 與 blocked-claim 糾正也是。

**那就是 backbone 的原始零件。** 差別只在:現在它只用來「糾正」,沒有用來「推進」。

**🎭 老韓:**

接得上。CASE 的狀態機每一步都是檔案狀態,而**檔案狀態是 harness 讀得到的**。

```
讀 02_Task_Queue → 有 IN_PROGRESS 但這一輪沒收掉
                 → turn_end 時注入「下一步是什麼」並觸發
```

不需要模型記得流程。**流程在磁碟上,harness 每輪讀一次。**

**🎭 小周:**

等一下。「harness 主動觸發下一輪」對我來說就是**它自己動起來了**。我沒開口它就跑。

**🎭 小晴(政策治理):**

小周這點正是我要談的。`policy-mediated` 的重點不在「自動」,在**政策寫在哪、誰能改**。

現在 `case-bridge` 已經有一個政策檢查:`isCaseProject(cwd)` —— 有 `CASE.md` 或
`00_Constitution` 才算數。**那就是專案層級的 opt-in,而且是使用者一次性宣告的。**

所以答案不是「自動 bootstrap」,是:

```
專案宣告一次(bootstrap 建立 CASE 骨架)
  → 此後 harness 依政策推進,不再問模型要不要
```

小周的專案沒有那個骨架,他永遠感覺不到。

**🎭 CK:**

這個我接受。我不想每次打 `/case`,但我願意在專案裡宣告一次。

**🎭 老魔(轉向):**

那我換個角度炸。**你們憑什麼認為「harness 推進」會比「模型自己決定」好?**

推進的內容還是文字,還是要模型讀了照做。你們只是把「模型要不要開始」換成「模型要不要照著
被塞進來的下一步做」。**同一個服從問題,換個位置。**

**🎭 老韓:**

不一樣,而且差別可以說清楚:

| | 現在 | 政策推進 |
|---|---|---|
| 誰決定下一步是什麼 | 模型(從一堆技能裡挑) | harness(從磁碟狀態算出來) |
| 模型要做的判斷 | 開放式:該用哪個框架、要不要用 | 封閉式:照這一步做 |
| 失敗長什麼樣 | 什麼都沒發生,看不出來 | 這一步沒做,**下一輪還會再說一次** |

**第三列才是重點。** 現在的失敗是靜默的;政策推進的失敗會重複出現,而重複出現的東西量得到。

**🎭 Vera:**

而且我可以量。注入的訊息有固定 `customType`,session 紀錄裡數得到「推進了幾次、推進之後
狀態有沒有前進」。**這是目前所有機制裡第一個能算出「遵循率」的。**

**🎭 老趙:**

我補一條稽核角度:推進紀錄本身就是證據。**「harness 說了下一步是 X,任務狀態有沒有從 A 變 B」**
是可稽核的因果對。現在的守衛只證明得了「我擋了」,證明不了「所以它做了」。

**🎭 阿凱(上游):**

要小心一件事:**推進邏輯不能重寫協定。** 下一步是什麼,應該從 CASE 的狀態機推導,不是
harness 自己發明一套。轉換表在上游,harness 只做查表。

**🎭 秦姐:**

同意,而且我加一條:**推進要能被關掉**。政策是設定,不是硬編碼。`enableCaseBridge` 已經存在,
推進應該是它底下的一個獨立旗標,預設值要由「第一次實測」決定,不是由設計時的直覺決定。

**🎭 小林:**

實作上我只有一個要求:**推進不能無限**。任務卡住時,推進會變成每輪都在說同一句話 ——
那就是迴圈。要有次數上限,跟既有守衛一樣。

## 本輪新發現

1. **`019fd702` 的方法論來自 CK 手貼的十萬字,不是 harness。** 唯一一次「看起來成功」是人工撐起來的。
2. **問題有正式名稱**:agent-proposed activation(實測 0/3)vs policy-mediated activation。
   2026 的共識是後者:deterministic backbone 持有流程,模型只填步驟。
3. **Pi 有 backbone 的零件而且已在用**:`sendMessage + triggerTurn`。目前只用來糾正,沒用來推進。
4. **政策的 opt-in 已經存在**:`isCaseProject(cwd)`。專案宣告一次,此後不必再問模型。
5. **老魔的反駁被具體回應**:推進不是消除服從問題,是**把靜默失敗換成會重複出現的失敗** ——
   而重複出現的東西量得到,靜默的量不到。
6. **這是第一個能算出「遵循率」的機制**:推進了幾次 / 狀態前進了幾次。

## 結論

下一步不是再加一道擋阻,是**把流程的持有權從模型手上拿回來**,在專案已宣告使用 CASE 的前提下。
