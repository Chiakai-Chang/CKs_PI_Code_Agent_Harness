**🎭 秦姐(先回答「先改協定還是先接上」):**

先改協定。理由是可判定性。

現在 `verify.py` 的 `success` 只看 5 條 errors,所以 harness 就算自動去跑它,得到的 `exit 0` **幾乎不帶資訊**。接上一個不會失敗的檢查,等於接了個綠燈裝飾。

但**不能直接把 10 條 warnings 全部升成 errors** —— 那會讓所有現存使用者的既有任務一夜之間全部驗證失敗。阿凱會殺了我。

**做法:加一個 `--strict` 旗標。** 預設行為完全不變(向後相容),`--strict` 時 warnings 視為 errors。本 harness 用 `--strict` 呼叫;別人的既有流程一個字都不用改。

**🎭 阿凱:**

這個我可以接受。向後相容 + opt-in,是能合併的形狀。

**🎭 老趙:**

我再加兩條該進上游的:

**一、`verify.py` 有副作用。** 第 133–148 行,狀態是 `DONE` 或 `REVIEW` 時它會**自動跑 `memory_tiering.manage_memory()`**,去改 `00_Constitution/learnings.md`。

**一個叫 verify 的東西不該改任何檔案。** 這讓驗證不可重複執行 —— 跑兩次結果可能不同,而且沒人預期「檢查」會寫東西。應該拆成 `--tier-memory` 旗標,或是獨立指令。

**二、沒有佇列層的驗證器。** `verify.py` 只驗一個任務包。**CASE 最核心的承諾「每次專注做一件事」,現在沒有任何工具驗得出來。**

該有的檢查:
- 同時最多一個 `IN_PROGRESS`
- 沒有跳號執行(`Task_003` 在 `Task_002` 還是 `PENDING` 時就 `DONE`)
- `DONE` 的任務不會被改回去

## SWOT

### Strengths
- `tool_call` 的 `{block, reason}` 已實測能改變行為
- CASE 協定完整,含狀態機、雙軌、驗證器、bootstrap
- `verify.py` / `verify.js` 兩版同步(5 errors / 10 warnings 一致)
- harness 在 `tool_call` 看得到全部工具呼叫 —— 稽核不需模型配合
- 外部證據支持三層防護:context 交付 / 工具呼叫 / 稽核記錄

### Weaknesses
- **15 條檢查裡 10 條不會讓驗證失敗** —— 偽收斂製造機
- `verify.py` 有副作用(自動改 `learnings.md`),驗證不可重複
- **沒有佇列層驗證器** —— 「一次一個」無法被檢查
- CASE 的 skill 在 catalog,無描述
- `case-bridge` / `AGENTS.md` 雙重條件互鎖
- MECE 佈線滿分仍未自啟 —— 證明「可見」不足

### Opportunities
- `verify.py` 已存在且從未被執行過 —— harness 接上即得
- `bootstrap.py` 同上
- `--strict` 旗標可向後相容地收緊
- 佇列不變式是純檔案檢查,可判定、可測試

### Threats
- **分叉**:重寫 CASE 會與上游分岔(`reference/oh-my-pi` 的疤)
- **升 errors 會弄壞現有使用者的任務**
- 無條件 bootstrap 會汙染不知情使用者的目錄
- 強制品質會得到敷衍(引用閘:編造 0→4)
- n=1 證據 → 必須預設安靜

| **Weaknesses** | **WO-1** 補佇列層驗證器(`--queue`),讓「一次一個」第一次變成可檢查的東西<br>**WO-2** `case-framework` 升 core,同時修 `pi-planning-with-files` 名稱不符造成的靜默降級 | **WT-1** `--strict` opt-in,預設行為不動 → 相容<br>**WT-2** bootstrap 不自動執行,只在多交付物且非 CASE 專案時把指令交給模型 → 不汙染小周<br>**WT-3** 每一步之間量一次,不疊著做 |

## 收斂決策

### A. 給上游 `Local-Agent-Workspace` 的改進(4 項)

| # | 改進 | 性質 |
|---|---|---|
| A1 | `verify.py` / `verify.js` 加 `--strict`:warnings 視為 errors | 向後相容 |
| A2 | 把 `memory_tiering` 副作用移到 `--tier-memory` 旗標背後 | **行為變更**,需在 CHANGELOG 標示 |
| A3 | 新增佇列層驗證 `--queue <02_Task_Queue>`:同時最多一個 `IN_PROGRESS`、不得跳號、`DONE` 不得回退 | 新功能 |
| A4 | 兩版驗證器同步(這是既有教訓:驗證器必須跟上協定,否則新的強制步驟靜默失檢) | 紀律 |

### B. 本 harness 的改動(依序,每步之間量一次)

| # | 改動 | 為什麼是這個順序 |
|---|---|---|
| B1 | `skillTiers.core` 加入 `case-framework`,並修 `planning-with-files` → `pi-planning-with-files` 的名稱不符 | 成本近乎零。**先量它夠不夠** |
| B2 | `case-bridge`:多交付物且非 CASE 專案時,注入 bootstrap 指令 | 打破互鎖,但不動使用者目錄 |
| B3 | harness 自寫 `action_log.jsonl` | 不依賴 B1/B2 成立,價值獨立 |
| B4 | 自動跑 `verify.py --strict` 並把結果送回模型 | 依賴 A1 先進上游 |
| B5 | 佇列不變式守衛(`tool_call` 擋跳號 / 擋第二個 `IN_PROGRESS`) | 依賴 A3;**只有量測顯示 B1–B4 不夠時才做** |

### 明確否決

| 方案 | 理由 |
|---|---|
| 全部原生重寫 CASE / MECE | 上游分叉。本 repo 已有 `reference/oh-my-pi` 的疤 —— 凍結分叉害它「找到」不存在的缺陷 |
| 直接把 10 條 warnings 升成 errors | 弄壞所有現存使用者的既有任務 |
| 無條件自動 bootstrap | 汙染不知情使用者的目錄;違反「預設安靜」 |
| 檢查 `recipe.md` 的 DoD 寫得好不好 | 強制品質會得到敷衍,已實測 |

## 妥協(明列)

1. **B2 仍是建議通道**,依 MECE 的反證有很大機率不會自己發生。它便宜,先做先量,但不能是唯一一步。
2. **B5 可能永遠不做** —— 如果 B1–B4 就夠了。這是刻意的:這一輪已經為「先蓋再量」付過兩次代價。
3. **A2 是行為變更**,不是純新增。上游需要 CHANGELOG 條目。
