## 第一輪:先確定問題不是「沒接好」

**🎭 老陳:** 我 dump 了 Pi 實際送出的系統提示。`<available_skills>` 有 45 個技能,
**每一個都有名稱和描述**,superpowers 的 14 個全在裡面,位置指向
`external/superpowers/skills/<name>/SKILL.md`。接線是好的。

**🎭 Vera:** 那就把「沒感覺」翻譯成數字。165 個 session,只計 assistant 的 `toolCall`
且參數路徑含 `.../<name>/SKILL.md` —— **45 個註冊技能裡 7 個曾被打開,38 個從未**。
superpowers 全部加起來 4 次,而且集中在 1–2 個 session。

**🎭 老魔:** 等一下。會不會是模型讀過技能但沒有透過 `read`?

**🎭 老陳:** 不會。Pi 的提示裡原文寫著 *"Use the read tool to load a skill's file"*。
在 Pi 裡**載入技能就等於讀那個檔案**,沒有第二條路 —— 沒有 `Skill` 這種一級工具。
這一點很重要,先記著。

**🎭 Vera:** 而且有一個乾淨的規律:**跨越多個 session 被打開的只有四個,
四個全部有 bridge 在動作當下說出它的名字** ——
`planning-with-files`(6 次 / 5 個 session)、`research-task-routing`、
`mece-autopilot`、`brainstorming`。其餘 38 個依賴模型自己從描述裡挑,結果是 0。

**結論:問題不在註冊,在觸發。**

## 第二輪:那為什麼在 Claude Code 裡「很有感」?

**🎭 小艾:** 因為那邊的載具不一樣。Claude Code 有一級的 `Skill` 工具,
而且 session 一開始就把 `using-superpowers` 整份灌進去,措辭是強制性的
(「只要有 1% 的機會適用就必須調用」)。**技能在那裡是被推的,不是被選的。**

**🎭 老陳:** Pi 這邊是:45 條描述放在一個 45,637 字元的系統提示裡,
然後說「符合描述時請自己 read」。同一批技能,兩種完全不同的觸發壓力。

**🎭 老鄒:** 所以擁有者說的「感覺不到」,精確講是 ——
**同一個 repo 的內容,在兩個 harness 上的到達率差了兩個數量級**。
這不是 superpowers 的問題,是我們這一層沒有把它接到動作上。

**🎭 老葛:** 有外部支持。Routine(arXiv 2507.14447)在 Qwen3-14B 上把多步工具呼叫正確率
從 32.6% 拉到 83.3%,機制正是**給腳本而不是給清單**。
我們自己的形狀路由就是照這個做的,而它是唯一有效的那個。

**🎭 小周:** 我插一句使用者視角:我裝完這個 harness,第一天最可能遇到的是 bug 跟實作。
而 `systematic-debugging` 和 `test-driven-development` 都是 **0 次**。
**我最需要的兩個,剛好在從未被打開的那 38 個裡面。**

## 第三輪:那要怎麼改?三條路,先吵清楚

**🎭 小艾:** 路線 A —— **把 superpowers 那幾個接進形狀路由**,照工作種類點名:
bug → `systematic-debugging`、實作 → `test-driven-development`、
宣稱完成前 → `verification-before-completion`。

**🎭 老聶:** 路線 B —— **砍預算**。`<available_skills>` 佔提示 44%(19,885 / 45,637 字元),
其中 38 個從未被打開。把它們降到只有名字的目錄層,可以回收一大塊。

**🎭 秦姐:** 路線 C —— **蒸餾出來的 16 個核心技能有 15 個連註冊層都不在**,
只在 120 個名字的目錄裡。要嘛升上來並被點名,要嘛承認它們是文件。

**🎭 老魔:** 三條一起做,你們就量不出來哪一條有效。這個 repo 上個月才因為
「同時改三件事」吃過虧。

**🎭 Vera:** 而且更難堪的是:**現在這個模型的噪音底線,呼叫數 sd 26.91**。
就算三條一起做,事後也分不出誰的功勞。**先做一條,而且要選那條有既有證據的。**

**🎭 老譚:** 選 A。因為 A 的證據不是推論 —— 是「被點名的四個技能是唯一被打開的」。
B 和 C 都是節流與整理,沒有任何證據說它們會讓技能被用。

## 第四輪:路線 A 的偽陽性長什麼樣(老譚的專業質詢)

**🎭 老譚:** 現在的分類器只判「多步 / 單步」,而且刻意保守 ——
106 個真實提示只有 17% 被判為多步。我要問:**加上「工作種類」之後,
一句「幫我看看這個錯誤」會不會每次都被塞一段 systematic-debugging?**

**🎭 小林:** 而且它會跟誰打架?`check-prompt-conflicts.py` 現在有 3 個共用詞警告。
再加三個技能名,共用詞會不會爆?

**🎭 老譚的裁決:** 三條防線:
1. **沿用既有的長度地板與保守判準**,不新增觸發面 —— 只在**已經判定為多步**的請求上
   追加一句「這個形狀對應哪個技能」。這樣觸發率不變,只是內容更精準
2. **一個請求最多點名一個工作種類技能**,取最強訊號,不列清單
3. **判不出來就不說** —— 沒有預設值。分類器對「不知道」保持沉默,是它唯一誠實的輸出

**🎭 老魔:** 那你等於只服務 17% 的請求。bug 修復通常是短句,不會被判多步。

**🎭 老譚:** 對,而這是**刻意的**。把觸發面從 17% 拉大到 100%,
就是把一句每輪都出現的話變成模型學會跳過的話 —— 上一版路由就是那樣失敗的。
**先服務 17%,量到效果再談擴大。**

## 第六輪:老魔的最後反對

**🎭 老魔:** 我的反對意見有三條,按強度排:

1. **你們在替一個沒有被證明的因果關係鋪路。** 「被點名的才被打開」是相關性。

3. **最根本的:擁有者說的「偏向 C.A.S.E.」,你們的解法是「讓 C.A.S.E. 的路由器
   去點名 superpowers」—— 那還是 C.A.S.E. 在中心。** 你們沒有解決他說的問題。

**🎭 秦姐(回應第 3 點):** 這一點我認為老魔說反了,而且是這一輪最重要的釐清。
**路由器不是 C.A.S.E.。** `task-shape-bridge` 是形狀路由,`case-bridge` 才是 C.A.S.E.。
路由器在**非** C.A.S.E. 專案裡才最活躍 —— 在 C.A.S.E. 專案裡它反而讓位
(`isCaseProject` 為真時整條路由站下來)。所以拿它去點名 superpowers,
正好是**在 C.A.S.E. 以外的世界**恢復技能層的價值。

**🎭 Vera(回應第 1 點):** 相關不是因果,同意。所以這件事要**帶著待驗證的假設出貨**:
先實作、先證明注入送達,**效果留給真實使用去累積**,而不是宣稱它有效。

**🎭 老陳(回應第 2 點):** 這一點是真的風險,而且**可以便宜地處理** ——
我們點名的是技能,不是把技能內容注入。模型讀了發現不適用就會放下,成本是一次 read。
比起現在的 0 次,一次 read 是可接受的代價。

## 第七輪(實作後補記):量測推翻了本輪自己的第一條限制

**🎭 Vera:** 決議第 2 條說「不擴大觸發面,只在已判定為多步的請求上追加一句」。
我照做了,然後在 **121 個真實開場提示**上量:

```
多步分類器命中     23   19%
工作種類命中       17   14%
兩者同時命中        7    6%   ← 決議第 2 條實際服務的範圍
```

(以上是**修剪樣式之前**的數字。依這份資料拿掉 `build` 與單獨的「開發」、
補上「根因」之後,用**實際出貨的模組**重量:多步 19%、工作種類 **13%**(除錯 9、實作 7)、
兩者同時 **5%**。結論不變,而數字必須是出貨那一版的。)

**🎭 老譚:** 而且是錯的那 6%。**除錯請求天生就是單步的** ——
「這個 parser 一直報錯,請找出 bug 並修復」是一件事,不是三件。
騎在多步上,`systematic-debugging` 會**繼續停在 0**,
也就是這整個改動要修的那個數字。

**🎭 老魔:** 那你們就是在推翻自己兩小時前的決議。

**🎭 秦姐:** 對,而且這正是量測存在的理由。決議第 2 條是**在沒有資料的情況下**
為了防止「每輪都出現的話會被學會跳過」而訂的 —— 那個顧慮本身沒有錯,
錯的是把它實作成「掛在多步上」。改成**自己的觸發條件 + 四道邊界**:
25 字地板、最多點名一個、判不出來就沉默、C.A.S.E. 專案整條讓位。
觸發率 13%,不是 100%。

**🎭 老聶:** 成本呢?

**🎭 Vera:** 單步時只注入**一句話**,沒有規劃腳本。相較於 `<available_skills>` 每輪的
19,885 字元,這是零頭。

**修正後的決議 2':** 工作種類的判斷**有自己的觸發條件**,觸發率 13%(實測 121 個真實提示),
已知偽陽性兩例(貼上的新聞內容含「錯誤」、一個 llama.cpp 支援度問題含 "implementation"),
兩例都寫進程式碼註解而不是藏起來。

**🎭 老趙:** 還有一件事必須記下來 —— **這一輪在動手時抓到一個活的缺陷**:
路由器注入給模型的名字是 `planning-with-files`,而 Pi 註冊的是 `pi-planning-with-files`。
2026-08-12 的改名修了兩個 SKILL.md 與兩份規則文件,**漏掉真正送到模型面前的那個 bridge**。
`tests/test_skill_names_resolve.py` 現在把 bridge 原始碼也納入檢查範圍。

**🎭 老莫:** 送達已證明,效果尚未證明。實跑一次(非 C.A.S.E. 專案,真實的 bug):
系統提示裡確實出現 `[task-shape] This reads like debugging: load the systematic-debugging skill...`,
**模型沒有打開那個技能,直接把 bug 修好了**。對這種一行 bug 來說那可能是對的選擇。
**效果要靠累積的真實 session 判定,不能靠這一次。**

# SWOT

## Strengths
- 技能層**接線是好的**:45 個註冊、有描述、路徑正確,不需要重建
- 已有一個**被證明會讓技能被打開**的機制(形狀路由),只需擴充內容
- `tests/test_skill_names_resolve.py` 已經在守「叫得出的名字必須註冊得到」
- 改動不碰 `external/`,上游更新不撕裂

## Weaknesses
- 45 個註冊技能裡 **38 個從未被打開**,每輪付 44% 的提示預算
- 蒸餾的 16 個核心技能有 15 個**連註冊層都不在**,比 superpowers 更遠
- Pi 沒有一級的 `Skill` 工具,載入技能=讀檔,觸發壓力天生比 Claude Code 弱
- 形狀路由只覆蓋 17% 的請求

## Opportunities
- superpowers 三個最有感的技能是**現成的、已註冊的**,只差被叫
- Viblux 的做法(入口文件把 session 推進 `docs/superpowers/specs/`)是**零程式碼**的第二條路
- 路由器在**非 C.A.S.E. 專案**才最活躍 —— 正好是擁有者說「偏向 C.A.S.E.」的解藥

## Threats
- 相關≠因果:被點名的技能也可能只是剛好落在模型本來想做的事上
- superpowers 的技能為別的 harness 寫,對本機小模型可能是噪音
- 擴大觸發面會讓路由變成背景雜訊,重演上一版的失敗
- 噪音底線 sd 26.91 —— 任何單次前後比較都讀不出效果

| **Weaknesses** | **WO(次之)**:入口文件路線 —— 讓 `docs/superpowers/` 有人指路。零程式碼,但屬於專案側而非 harness 側,先擱置 | **WT(暫緩)**:降級 38 個技能、蒸餾技能升層。便宜但無證據,且會污染 A 的量測 |

## 這一輪最重要的三句

1. **問題不是沒接好,是沒有人叫它** —— 45 個註冊、38 個從未被打開,而被打開的四個全部有 bridge 當場點名。
2. **同一批技能在兩個 harness 上的到達率差兩個數量級**,差別是載具:Claude Code 推,Pi 讓你自己選。
3. **「偏向 C.A.S.E.」的解藥不在 C.A.S.E. 裡** —— 形狀路由在非 C.A.S.E. 專案才活躍,那正是技能層該復活的地方。
