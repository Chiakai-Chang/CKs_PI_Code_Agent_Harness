## SWOT

### Strengths
- `sendMessage + followUp + triggerTurn` 已在本 repo 運作(async-exec 喚醒、兩個糾正守衛)
- 下一步可從檔案狀態純查表推導,零推測
- 政策 opt-in 已存在:`isCaseProject(cwd)`
- 五條 CASE 守衛已就位,推進器推出去的每一步都有守衛接著
- **第一個能算出遵循率的機制**

### Weaknesses
- 推進內容仍是文字,模型仍可不照做(老魔的核心反駁)
- `--print` 探針測不到多輪推進
- 推進器會主動觸發回合 —— 比擋阻更大的行為改變
- 證據仍是 n=1 等級

### Opportunities
- 文獻與 Anthropic 2026 指引同向:deterministic backbone + LLM at specific steps
- `verify.py --strict` 剛做好,推進器與它查同一組檔案
- CK 的真實專案是天然測試場,而且他願意在專案裡宣告一次

### Threats
- **推進變成迴圈**:任務卡住時每輪重複同一句
- **GateGuard 的疤**:沒人跑過的東西預設開啟
- 推進邏輯自創 = 與上游協定分岔
- 又一個「單元測試綠、實測沒發生」的機制

## TOWS

| | **Opportunities** | **Threats** |
|---|---|---|
| **Strengths** | **SO-1** 用既有的 `triggerTurn` 做 backbone,下一步查 CASE 狀態表得出<br>**SO-2** 推進與 `verify --strict` 查同一組檔案 → 推進說的下一步,驗證器認得 | **ST-1** 同一個下一步連推 3 次不前進就停並升級(沿用既有退場形狀)<br>**ST-2** 只查表不自創 → 不分岔 |
| **Weaknesses** | **WO-1** 模型仍可不照做 → 但失敗會**重複出現**,而重複的量得到;這正是遵循率的來源<br>**WO-2** 探針測不到 → 用 CK 的真實專案量,注入帶固定 `customType` 供事後統計 | **WT-1** 預設**關**,由第一次實測決定要不要開<br>**WT-2** 只在有 CASE 骨架的專案生效,其他人零感知 |

## 收斂決策

**做:佇列推進器(queue advancer)**

```
政策    專案有 CASE 骨架(isCaseProject)且旗標開啟
時機    turn_end
判斷    讀 02_Task_Queue → 目前任務狀態 + 缺哪個檔案 → 查表得出下一步
動作    sendMessage(下一步, { deliverAs: "followUp", triggerTurn: true })
上限    同一任務同一下一步連續 3 次無前進 → 停止並升級
預設    關(enableCaseAdvancer: false)
量測    固定 customType;遵循率 = 狀態前進次數 / 推進次數
```

**明確不做**

| 方案 | 理由 |
|---|---|
| 自動 bootstrap | 汙染;且啟動是決策,政策 opt-in 才是解 |
| 推進器自創下一步 | 與上游分岔 |
| 預設開啟 | GateGuard 的疤 |
| 無上限推進 | 那是迴圈 |

## 妥協(明列)

1. **模型仍可不照做。** 推進器不消除服從問題,它把靜默失敗換成可計數的失敗。
2. **預設關,所以它一開始不會幫到任何人** —— 包括 CK,除非他自己打開。這是刻意的。
3. **老魔的賭注記在案上**:第一次量測的遵循率**很可能不是 1.0**。先說,再量。
