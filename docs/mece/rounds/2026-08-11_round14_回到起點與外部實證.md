## 第二輪:外部實證說 A 路線可行,而且指出我們缺什麼

**🎭 老葛:** 三份外部資料,直接對應擁有者的目標。

**(1) Harness-Bench(5,194 條軌跡)** —— 最重要的一句:

> agent capability should be reported at the **model–harness configuration level**
> rather than attributed to the base model alone

**這正是 CK 剛才問的「兩個互相優化好不好」的學術版答案:能力本來就是一個配對的屬性。**
所以互相優化不是錯,**錯的是不記錄配置就報數字。**

它量到的五種反覆失效:

| 症狀 | 佔比 | 我們有沒有 |
|---|---|---|
| Output contract violations | 36.4% | 部分(DoD 驗收物守衛) |
| Tool/recovery failures | 24.6% | ❌ **沒有** |
| Evidence gaps | 14.6% | 有(引用閘) |
| **Artifact commitment failures**(有推理沒產出) | 11.1% | ✅ **今天才做的驗收物守衛** |
| State preservation | 9.3% | 部分(目標重述,未證明) |

**🎭 老趙:** 第四項逐字命中我們 live4 那個 run —— 模型**寫出了完整報告**,被擋之後
**再也沒重寫**,最後空著進 REVIEW。**那是一個有名字、有base rate 的已知失效,不是我們的特例。**

**(2) 8B 本機模型 53% → 99% 的工程手冊**(Forge 的消融測試)

| 機制 | 量到的增益 | 我們有沒有 |
|---|---|---|
| **Response validation & rescue parsing** | **+8–12pp** | ❌ **完全沒有** |
| Targeted retry nudges | +6–9pp | ✅ 就是我們的拒絕文字 |
| **Step enforcement & prerequisites** | +5–8pp | ✅ **就是階段閘** |
| VRAM-aware context management | +3–5pp | ✅ compaction bridge |

**🎭 老魔:** 等一下。**增益最大的那一項我們一個都沒有**,而我們花整天在調第二和第三項。

**(3) 而最大的一件事是架構性的:**

> 允許模型在「輸出文字」和「呼叫工具」之間自己選,completion 會從 100% 掉到 **最低 4%**。
> 修法:自動注入一個合成的 `respond` 工具,**強迫模型永遠處於 tool-calling 模式**。

**🎭 老陳:** 這正是我們記了好幾條疤的東西 —— 「假工具呼叫迴圈」、「JSON 假呼叫」、
「宣布下一步然後結束回合」。**我們一直在做症狀處理。**

**🎭 老葛:** 而且有獨立文獻佐證。arXiv 2605.09252 量了 3B–8B 開源模型:
**「該呼叫工具卻沒呼叫」的落差是 26.5–54%(算術)、30.8–41.8%(事實問答)。**
關鍵句:**問題不在辨識** —— 模型的 hidden state 清楚知道需要工具 ——
**斷在「把那個信念變成 tool-call token」**,而且信念接近確定時依然斷。

**🎭 小婕:** 那結論很清楚:**這一層不該在 harness 修,該在推論服務端修。**
`tool_choice="required"`、grammar/GBNF 約束解碼、prefill 引導 ——
這些都在 llama.cpp / vLLM 層,而**我們在 bridge 層寫了幾百行去接住它的後果。**

## 第三輪:那該重構嗎?有沒有衝突、重疊、更新風險

**🎭 老方:** CK 問了六個具體問題,逐一回答。

**有沒有重疊?** 有,而且現在看得出來:

* 階段閘、轉換守衛、驗收物守衛 —— 三個都在管「順序與完整性」。**不重疊,是同一族的三個切面**,可接受

強模型寫 `role.md` / `recipe.md`,弱模型執行。今天的任務憲法注入正好送這兩個檔案。

## 收斂:這一輪的整合結論

1. **停止技能遷移** —— 它解的是探針假象。寫下觸發條件:
   **若真實專案的 session 出現 harness 路徑污染率上升,再回來做。**
2. **量「宣布動作卻沒呼叫工具」的比率** —— 從既有 session log 數,零成本,
   而且它決定第 3 項值不值得
3. **若比率顯著:處理 tool-vs-text 歧義** —— 在**服務層或 Pi 層**,不在 bridge 層
4. **把校準參數移出程式碼** —— Harness-Bench 的配置層報告原則的直接落實
5. **合併目標重述與任務憲法**(Task_024)—— 消除已識別的重疊
6. **A+C 的第一個乾淨實驗**:我寫一份認真的任務包,放在**真實專案**裡,讓 Pi 執行

**明確拒絕:照抄 8B 手冊的四根支柱。** 沒有噪音底線之前,pp 是別人的數字。

```

**受影響的 session               : 6  (6% 的 session)**
```

**🎭 老魔:** 所以那個「最重要的發現」縮水了十七倍。

**🎭 Vera:** 縮水,但沒有消失。而且抽樣裡有**模型自己描述這個失效**的三筆:

> 「我將先讀取專案核心文件」→ 然後輸出 `<read><path>…</path></read>` **當文字**
> 「我遇到工具呼叫問題,系統連續三次自動糾正。**讓我改用文字說明**」
> 「每次我輸出工具標籤(XML/JSON),系統都…」

**🎭 老葛:** 這是引用外部數字時該有的紀律的示範:
文獻的 26.5–54% 是 3B–8B 模型在算術/事實問答上量的,**不是我們的配置**。
Harness-Bench 自己就說能力是配對屬性 —— **借來的數字不能當成自己的。**

**🎭 老莫:** 而方法論上,這一輪做對了三件我今天反覆做錯的事:

# SWOT

## Strengths
* **協定與執行分層是健康的**,而且今天多了一條可機械判定的分界規則
* 守衛有實測價值:圍堵擋下真實污染(含直譯器繞過)、轉換守衛擋下兩次跳步
* **量測工具鏈成形**:`mine-session.py`、變異掃描、prompt dump ——
  今天三次「我的數字錯了」全是它們抓到的
* 1289 條測試、0 變異存活者(已納入的模組)、CI 綠

## Weaknesses
* **沒有噪音底線**(同題同臂 42 vs 4 次呼叫)—— 所有效果宣稱的天花板
* **校準參數寫死在出貨程式碼裡**,換模型時會安靜地失效
* **探針設計曾製造它自己要量的失效** —— 而且花了一整天才發現
* 目標重述與任務憲法**功能重疊**,尚未合併
* 缺 rescue parsing / 工具呼叫恢復(Harness-Bench 的 24.6% 類別)

## Opportunities
* **外部實證支持 A 路線可行**(8B 從 53% 到 99%),且指出我們缺的那一項增益最大
* **C 不需要新機制** —— 任務憲法注入已經在送 `role.md` 與 Local DoD
* Harness-Bench 的「配置層報告」直接給了「兩個互相優化」的正解
* 擁有者的真實 session 是**現成的、乾淨的量測基礎**,而我一直在用暫存目錄

## Threats
* **繼續優化探針而非產品** —— 今天已經發生一次
* 借用外部 pp 數字當自己的收益 —— 今天差點發生
* SD 卡:repo 在可移除媒體上,斷線時「死掉的 run」看起來像「零結果」
* **擁有者的耐心** —— 這是真實約束,而它已經被明確表達
