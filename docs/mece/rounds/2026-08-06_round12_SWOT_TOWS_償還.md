**🎭 小江(先講最便宜的那一個):**

13 個一次性解析腳本、兩次錯誤結論 —— 這是**唯一一個做一次就永久消失的問題**。

一支 `scripts/session-report.py`:給 session 檔或目錄,印出工具統計、守衛開火次數、
技能載入、檔案內網址、custom_message。**兩次錯誤結論都是它會擋掉的形狀** ——
因為它會印出「掃到幾個檔案」,而不是靜靜地回 0。

**🎭 Vera:**

而且它同時償還量測債的一部分。五個未觀察到的機制,現在要驗就得每次手刻查詢;
有工具之後,**每次真實 session 之後跑一次,累積證據不必特地設計實驗。**

**🎭 老趙:**

知識落地我要排在效率之前。**Task_001 的 output 與 retro 現在只存在於一個 gitignore 的目錄裡。**
機器重灌、`git clean -xdf`、暫存清理,任何一個都會讓它消失。

而且這不是一次性問題 —— **每一個未來的任務都會有同樣的洞。**

**🎭 秦姐:**

那要小心不要違反協定。C.A.S.E. 把佇列定義為代理工作區是有道理的:任務包裡有大量
中間狀態,全部進版控會淹掉歷史。

**分開處理:工作區留在佇列,結論抽到 `docs/`。** 需要的是一個「抽取」動作,不是把
gitignore 拿掉。

**🎭 老陳:**

那可以做成 `verify.py --strict` 通過時的一個提示,或是一支 `scripts/case-harvest.py`
把 `output.md` / `retro.md` 收成一份 `docs/case/<task>.md`。**後者可判定、可重跑。**

**🎭 老魔:**

我來擋一下。**你們正在為一個只跑過三個任務的流程建工具鏈。**
`case-harvest.py` 是為了修一個「因為 gitignore 所以會遺失」的問題 ——
**但真正的問題是佇列裡的東西該不該進 docs,而那是每個任務都不同的判斷。**

自動抽取會抽出一堆沒人要看的中間產物。

**🎭 老趙:**

我接受這個限制,但至少要**列出未抽取的任務**,不要靜默。一支腳本回報
「Task_001 有 output.md/retro.md,而 docs/ 裡沒有對應紀錄」就夠了 ——
**抽不抽由人決定,漏不漏由程式看著。**

**🎭 老韓(REVIEW 的分類):**

我的提案很小:`--strict` 通過時,在任務目錄寫一個 `machine-check.txt`,
記下通過的時間與驗證器版本。**CK 看到有那個檔案的 REVIEW,就知道只剩判斷。**

**🎭 小晴:**

我反對再多一個檔案。協定的檔案清單已經八項,再加就是協定漂移 ——
而阿凱剛才才說過不要分岔。

**🎭 老趙:**

那放進既有的 `log.md` 或 `feedback.md`?**`feedback.md` 的定義是「只由 Checker 或人類寫」**
—— 機械驗證正是一種 Checker 行為。

**🎭 阿凱(上游):**

`feedback.md` 我可以接受,那不算新增檔案。但**這是協定語意的擴充**,要回饋上游,
不能只在本地做。

**🎭 CK 的時間:**

我要的其實很簡單:**打開佇列,一眼看出哪些只等我點頭、哪些還沒做完。**
用什麼檔案我不在乎。

**🎭 老魔(最後一擊):**

那我問一個沒人問的:**這三件事,哪一件會讓下一個任務更早發現錯誤?**

* session 報表 → **會**。兩次錯誤結論都是它擋得掉的。
* 抽取漏檢 → 不會。它防的是遺失,不是錯誤。
* REVIEW 分類 → 不會。它省的是 CK 的注意力,不是錯誤。

**優先序自己就出來了。**

## SWOT

### Strengths
* 八個機制有五個已在真實 session 被觀察到開火,證據紮實
* `verify.py --strict` / `--queue` 已可用,機械檢查有現成工具
* 每個任務都留下 output/retro/log,結構一致,便於自動處理

### Weaknesses
* **五個機制從未被觀察到開火**
* **跨 bridge 擋阻交互無任何檢查**,唯一協調靠人記得
* **13 個一次性解析腳本,兩次錯誤結論**
* **`02_Task_Queue/` 未進版控**,Task_001 的產出隨時可能消失
* REVIEW 累積成人類待辦,與原始需求相反

### Opportunities
* 一支 session 報表工具同時償還「解析錯誤」與「量測債」兩筆
* `feedback.md` 已存在且語意相容,可承載機械檢查結果而不新增檔案
* 每次真實 session 都是免費的觀察機會,只要有工具就能累積

### Threats
* **為只跑過三個任務的流程過度建工具**(老魔)
* 自動抽取會產生沒人看的中間產物
* 協定語意擴充若不回饋上游就是分岔
* 「本次未觀察到」被當成「不會發生」——Task_002 已經犯過一次

## TOWS

| | **Opportunities** | **Threats** |
|---|---|---|
| **Strengths** | **SO-1** `scripts/session-report.py`:一支工具同時解決解析錯誤與量測債累積<br>**SO-2** 每次真實 session 後跑一次,五個未觀察機制靠累積而非特地設計實驗來驗 | **ST-1** 只做報表,不做自動抽取 —— 抽不抽是判斷,漏不漏是程式的事<br>**ST-2** 報表明確印出「掃到幾個檔案」,讓假的零無法偽裝成真的零 |
| **Weaknesses** | **WO-1** 未抽取任務只**列出**,不自動搬 → 避免中間產物淹沒 docs<br>**WO-2** 跨 bridge 交互:報表統計同輪出現幾則 `custom_message`,把「本次未觀察到」變成可累積的數字 | **WT-1** 不新增協定檔案;REVIEW 分類延後到有第二個任務卡住時再談<br>**WT-2** 不為三個任務建完整工具鏈 —— 只做一支報表 |

## 收斂決策

**做(依序,只做第一項就停下來量):**

| # | 項目 | 為什麼是這個順序 |
|---|---|---|
| **D1** | `scripts/session-report.py` —— 給 session 檔/目錄,印出工具統計、守衛開火、技能載入、檔案內網址、`custom_message` 分佈,**並印出掃到的檔案數與檔名** | 唯一一項會讓**下一個任務更早發現錯誤**的。兩次錯誤結論都是它擋得掉的形狀 |
| D2 | 未抽取任務的漏檢(併進 D1,一個旗標) | 防遺失,成本近乎零 |

**明確延後:**

| 項目 | 理由 |
|---|---|
| `case-harvest.py` 自動抽取 | 抽什麼是每個任務不同的判斷,自動化會產生沒人看的東西 |
| REVIEW 的機械/判斷分類 | 目前只有兩項卡住。**等第三項卡住再說** —— 現在做是為想像中的規模建設 |
| 跨 bridge 擋阻協調機制 | 先用 D1 累積「同輪幾則訊息」的數字,有數字再設計 |

**明確不做:**

| 方案 | 理由 |
|---|---|
| 讓本地模型當 Checker | 今天謊報兩次、走錯目錄三次,有紀錄。用已知會捏造的東西驗收是自欺 |
| 把 `02_Task_Queue/` 移出 gitignore | 違反協定對工作區的定義,且會用中間狀態淹沒歷史 |

## 妥協(明列)

1. **五個未觀察到的機制不會因為 D1 就被驗證** —— D1 只是讓每次真實使用都能累積證據,
   不是替代實驗。
2. **跨 bridge 交互仍然沒有檢查。** 只是從「靠人記得」變成「有數字可以看」。
3. **Task_001 的 output/retro 仍在 gitignore 目錄** —— D2 只會提醒,不會搬。
