## 誠實的偏移判定

**你上一次真正得到東西,是引用閘 / 深度閘 / 產出閘 —— 那些有實測、模型會照做。**

在那之後:

```
Task_001  推進器          → 為 R1/R7/R9 而做,量測 0/3
Task_002  量測            → 得到一個數字,以及一個被汙染的結論(見下)
Task_003  cwd 修補        → 為了讓 Task_002 能重測
session-report.py         → 為了讓「我」量得準
```

**每一步都有正當理由,但你自己一件都沒拿到。** 我離需求已經隔了三層:
你要的能力 → 推進器 → 量測障礙 → 量測工具。

這不是災難,但必須說出來,否則下一輪會繼續往下鑽。

## Task_002 的結論被我自己汙染了

`git log --diff-filter=A -- 00_Constitution/core.md` → `c6cc1ea`,**今天**。
在那之前 harness repo 沒有 `02_Task_Queue`。

Task_002 量測時,模型解析到 harness 根目錄,**在那裡找到了一個看起來完全合理的佇列**
(`Task_001_queue_advancer`,狀態 REVIEW),於是開始對它動手,被 one-at-a-time 守衛與
目錄圍堵擋下。

**那個誘餌是我幾小時前製造的。**

兩個成因要分開:

| 成因 | 是否既有 | 證據 |
|---|---|---|
| 模型把相對路徑解析到 harness 根 | **是**,今天三次,其中一次在 bootstrap 之前(寫進 vendored submodule) | 三段 session 紀錄 |
| 解析過去之後**剛好有佇列可以動手** | **否 —— 我造成的** | `c6cc1ea` |

沒有第二個成因,模型解析過去會找到**空的**,可能就自己修正了。

**所以「遵循率 0/3」不能直接當成推進器的成績。**

## 因此下一步改了

原訂 Task_003 是「在擋阻理由裡解釋 harness 路徑」。那修的是成因一,而且是文字通道 ——
這個 session 已經三次證明文字會輸。

**改成:先在沒有誘餌的條件下重測。** 成本是暫時把 harness 的佇列移開,比實作一個新機制便宜
一個數量級,而且可能直接證明推進器是有效的。

**先量,再說 —— 這是面板自己訂的規矩,而我差點跳過它去實作。**

## 這一段真正的收穫

**一、`session-report.py` 是唯一一個會讓下一個錯誤更早被發現的東西。**
兩次錯誤結論都是「看到 0」,而它先印掃到哪些檔案。它服務的是開發過程,不是你 ——
但沒有它,前面兩次錯誤結論會變成常態。

**二、破壞測試需要它自己的檢查。** 本 session 五次「破壞了卻沒被抓到」,其中三次是破壞
根本沒套用(shell 回傳上一個指令的結果),兩次是斷言鬆到分不出對錯。現在有 `brk.py`
會先驗證樣式存在。

**三、假的安心比沒有檢查更糟。** 漏檢功能第一次真實使用就回報「全部都有」,而那份 retro
的三條上游回饋完全沒進版控。已改成列出全部並明說「被提及不等於被保存」。

**四、我自己製造了被量測的環境缺陷。** 這是最該記住的一條:**建立測量環境的人,也在改變被測對象。**
