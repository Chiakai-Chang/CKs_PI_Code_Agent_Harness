# 概念對齊:需求是「沒先規劃就開始」,不是「搜太多次」

日期:2026-08-06
狀態:**對齊文件,不是設計文件。** 設計與實作在此之後另立。

## 1. 需求原文

> 我發現目前 pi 雖然搜尋網路能力正常,但**還是會直接開始搜尋網頁**,然後煞有其事的搜尋可能十幾次,然後給我一個結論。
>
> 但明明有 Superpowers、Planning-with-Files 跟我設計的 C.A.S.E._Framework 等等,理想上應該是先按照我們的「核心功能與 5 層 Harness OS 架構」研究、釐清甚至完善我們的任務需求,甚至啟動 MECE-Autopilot 來優化,然後後續接上 Superpowers 流程、按照 C.A.S.E._Framework 將任務切分,用 Planning-with-Files 來做規劃,**每一次小任務都盡可能高品質的完成,而不是一次 round 完成**。
>
> 這幾次搜尋好像**都沒有留下文件**,非常的可惜。而且都存在記憶體,當然天然的任何模型都會控制想要趕快結束話題。**用文件拆分小任務,才能在最適當的 ctx 過程,真的用心地去處理**,所以我才設計 case 框架。
>
> 每次專注做一件事,做完復盤,有發現就增加 task queue,持續重複的用最高品質與努力不懈的匠人打磨精神,**求真求完美的盡可能將工作有憑有據、有成果的來完成**才對。

### 澄清(2026-08-06,擁有者本人)

> 他多搜幾次是好的啊?越多越好不是?**我抱怨的是他沒有先規劃就開始,不是抱怨他搜尋太多次。**

**搜尋次數不是問題。第一個動作是搜尋而不是規劃,才是問題。**

## 3. 兩種不同的失效,不要混為一談

### 3a. 擁有者的真實 session(`019fd29d`,互動,3 turn)

```
40 tool calls = 38 web_search + 2 web_open + 0 write/edit + 0 read
```

**一次 `read` 都沒有,零個 skill 被載入。** 從 Layer 3 直接起跳。

### 3b. 量測探針(`multi-step-methodology`,`--print`,單輪)

```
run1  research-task-routing, planning-with-files, planning-with-files
run2  research-task-routing
run3  research-task-routing, pi-planning-with-files, planning-with-files
```

**skill 有載入、有被讀,然後裡面的指令被跳過**(檔案內網址 0/0/0)。

### 結論

這是兩個不同的問題。探針**沒有重現**擁有者遇到的那一個。任何「探針分數變好」的宣稱,
都不能直接推論成擁有者的問題被解決。

### 誤推是怎麼發生的

我從真實 session 觀察到 `2 open / 38 search`,把它讀成「搜太多、讀太少」,做了一個以
**搜尋次數**為觸發條件的閘。擁有者從未抱怨搜尋次數。

第二個放大因素:我請擁有者在「產出證據」與「流程遵循度」之間二選一,他選了產出證據。
那是個好判準 —— 但它衡量的是**一輪的產出品質**,把 R7/R9 的「不要一輪」整個排除在外。
**那個選項是我遞出去的,框住後續每一步的也是它。**

## 5. 真正的缺口:Layer 1 從未被到達

README 的架構寫得很明確:

```
Layer 1: Socratic Framing (需求研討與對立審查層)
  • grilling-protocol (蘇格拉底一問一答需求釐清門控)
  • contrarian-review & adversary-review
        ↓
Layer 3: Execution & Repair OS (執行管束、網頁檢索)
```

**實測:真實 session 與三個探針 run,沒有任何一次載入 Layer 1 的技能。** 流程一律從
Layer 3 起跳。

`grilling-protocol` 的名字裡就有「門控」,但它是一份**建議性技能文字**,不是門。

而本輪最重要的實測發現正好說明為什麼建議不夠:

> 三個 run 都載入並讀了 `research-task-routing`,它裡面有一張**強制附 `Source` 欄位**的表。
> 檔案裡的網址是 0/0/0。而那條指令**前一輪已經換過形狀**(從句子改成表格空白欄)。
>
> **寫在 skill 裡的文字,在「要做事」的那一刻會輸。`tool_call` 的拒絕不會。**

## 6. 已同意的方向

**把 Layer 1 從建議變成門,把單輪變成 queue 迴圈。**

三件事:

1. **前置門控(R1/R2)**:多交付物的請求,第一個廣義工具呼叫直接 `block`。理由文字指明
   兩條路擇一:先做需求釐清(Layer 1),或先寫 plan。滿足其一才放行。
2. **queue 作為工作單位(R5/R7/R9)**:`task_queue.md`。每輪只准處理一項;該項沒收掉,
   不准開下一項。
3. **輪末復盤與 queue 增長(R9)**:收掉一項時要求寫下發現;新發現進 queue。

### 深度閘的處置(已同意)

**留著但降級。** 不再計入需求進度。理由:它從未開火,而「搜了 8 次一頁沒讀」確實不好,
但它不是擁有者要的東西,不該被當成進度回報。

## 8. 已知限制,先寫在前面

1. **`turn_end` 沒有回傳型別。** 輪末做出的判斷無法當場送達模型,必須排隊到下一個事件。
   這直接限制第 3 件事(輪末復盤)的實作方式。
2. **`pi --print` 是單輪。** R7/R9 的整個迴圈在探針裡**不可能出現** —— 不是沒量到,是量不到。
   驗證只能靠擁有者實際互動使用。
3. **前置門控會 block。** 本 repo 對此有疤:GateGuard 上線後擋掉每個 session 的第一條
   bash 指令。任何新的門都必須:門檻寬、fail open、擋滿 N 次就退場,並在預設開啟前實測。
4. **一個閘會製造它自己的失效模式。** 引用閘讓檔案內網址 0→10 的同一個 run,編造的網址
   也從 0→4(全是購物網站搜尋端點)。前置門控上線後必須同樣檢查它把行為推到哪裡去了。
