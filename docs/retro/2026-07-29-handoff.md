## 五、下一步（照這個順序）

### 1. 重試量測 —— 進行中，尚無數據

`scripts/probe-retry-recovery.mjs`（已寫好、只跑過煙霧測試）。

要回答的是：**Guard 6 現在送的長篇糾正，到底有沒有用？**

注意一個容易搞錯的前提：`sendMessage(deliverAs:"followUp", triggerTurn:true)`
**本來就會重新觸發一輪**，所以現行 Guard 6 已經是一種重試，只是附帶訓話。
真正要比的是訓話有沒有幫助，不是「有沒有重試」。

四個 arm，用今天真實捕捉到的捏造文字構造失敗狀態：

```
A  長篇糾正 + 重新觸發    ← 現行
B  最小指示 "Use the read tool now."
C  純續行 "Continue."
D  丟掉那輪捏造、重送原請求  ← 上界對照
```

判讀：

```
D 高、A/B/C 也高    -> 失敗獨立，重試有效。Guard 6 把長篇糾正換成最小指示
D 高、A/B/C 明顯低  -> 捏造留在 context 會污染後續。正解是移除那輪，
                       但 Pi 沒有這個 API，要另尋機制
D 也低              -> 不是獨立、也不是污染，重試怎麼調都沒用
```

**「重試一次把 9% 降到 0.8%」那個算術建立在「獨立」這個未驗證假設上**，這次量測就是為了驗它。
今天已經有六個結論栽在未驗證假設上。

執行注意：每個請求 10–90 秒，四個 arm × n=25 是好幾小時。依可用時間決定 n，
**並且回報時要寫出實際用的 n**。另外失敗狀態是構造的（真實文字、但由腳本塞入），
若 A/B/C 明顯低於 D，要再用自然發生的失敗做小樣本確認才能下結論。

**n=3 煙霧測試（2026-07-29 收工前，資料無效，僅用來驗腳本）**：

```
A_long_correction  0/3
B_minimal          1/3   （兩次失敗是模型發明語法：<read_file path="..."/>）
C_bare             0/0   3 次全部 error
D_drop_bad_turn    0/0   3 次全部 error
```

C 與 D 整個 arm 掛掉，原因是 undici 預設 5 分鐘逾時——那兩個 arm 沒有「已經做完」的暗示，
模型會生很長的散文。**把逾時記成 error 是錯的**：一個生了五分鐘散文的回合實務上就是失敗，
記成 error 會讓最容易失敗的案例系統性消失，而消失的正是整個實驗依賴的上界對照。
已修：逾時計為 fail（`PROBE_TIMEOUT_MS`，預設 240000）。修完之後**還沒重跑**。

## 六、量測紀律（今天六個錯換來的）

1. **先量目標的真實值，再設計 fixture。** 「差不多這麼大」量出來的是那個負載的性質，不是目標的。
2. **釘死量測輸入**（`git show <commit>:`），不要指向工作區活檔——寫報告會改動它。
3. **n=12 起跳**，換配置要在同一時間窗內 ABAB 重測。
4. **兩邊都必須落在非地板區**，同時觸底時的「沒有差別」是量測失效不是結論。
5. **差異要先過統計檢定再當訊號**，8/8 對 6/8 是 8 次裡差 2 次。
6. **結論本身要通過合理性檢查**：262k 的模型只能用 26.8k，這句話該在跑任何統計之前就被攔下。
7. 健康檢查要打真正要用的端點，不是隨便一個會回 200 的。
