## 三、已經驗證過的，不要重驗

這四點是實測而非推論，重驗只是浪費時間：

1. **extension 的 event loop 在 agent 閒置時存活**，脫離的 `setTimeout` 準時觸發。
2. **`pi.sendMessage(msg, { triggerTurn: true, deliverAs: "followUp" })` 能喚醒閒置的 agent。**
   完整事件鏈實測通過：`agent_start → turn_start → [custom message] → assistant 回應
   → turn_end → agent_end → agent_settled`。
3. **detached 子進程活過父進程結束。** 父進程呼叫 `process.exit(0)` 後，子進程仍在
   六秒後完成並寫出狀態檔；失敗案例正確回報 exit 3 而非 0。
4. **Pi 的 loader 與 `node --test` 都解析 `./x.ts` 這種明確副檔名的 sibling import。**
   這是計畫能用真 TDD 的前提。

## 四、會踩的坑（都是「看起來更自然的那個版本是錯的」）

**1. 不要把 `startDetached` 簡化成 `stdio: ["ignore", fd, fd]`。**
那是比較直覺的寫法，而且在 Windows 上**每次都產生空的輸出檔**——detached 子進程
不可靠地繼承 file descriptor。計畫裡用的是 shell 層級重導加 `stdio: "ignore"`，
這也是 Node 官方文件建議搭配 `detached` 的組合。

**2. 不要用 `./x.js` 寫法引用 sibling 模組。**
`deep-research-bridge` 是這樣寫的（在 Pi 的 loader 下可行），但**在 `node --test`
下不解析**，會讓這個 bridge 的單元測試全部找不到模組。本 bridge 一律用 `.ts`。

**3. 不要以為 exit code 可以靠輪詢 PID 取得。**
detached 的子進程結束後就消失了，只能知道「死了」，不知道「怎麼死的」。
計畫用 shell wrapper 寫 `.rc` 哨兵檔。**`readExitCode()` 回 null 不等於成功**——
那代表工作根本沒跑完（被砍、斷電）。

**4. 不要在缺少量測時填佔位值。**
`stateBlock` 的 GPU 欄位是可選的，v1 直接省略並印 `GPU state: not probed in v1`。
餵模型假事實比不餵更糟：那個欄位存在的唯一理由就是讓模型不必猜，
而一個自信的錯誤數字正是它要取代的東西。同理，`localModel: "exclusive"` 在 v1
**直接拒絕**，因為沒有 GPU 探測就無法誠實檢查。

**5. `lease.ts` 在 v1 是刻意的死碼。**
它完整實作且測試通過，但 v1 拒絕 `exclusive`，所以租約永不取得、`beat()` 永不呼叫。
**不要刪掉它，也不要去接一個無事可做的 heartbeat 計時器。** 它是 v2 功能的
已完成的那一半，另一半是 GPU 探測。

## 五、已經決定的，不要重新討論

- **資源模型收斂成單一軸線** `localModel: none | shared | exclusive`。不是泛用資源模型。
- **`exclusive` 是拒絕不是排隊。** 常駐模型佔 80.76 GiB、carve 96 GiB，第二個本地模型
  塞不進去，排隊只會製造死鎖。
- **PARK 不是原語。** 它就是模型不再發工具呼叫、讓這輪自然結束。不要去實作一個
  不存在的 park 機制。思考步驟是建議性的：機制保證「無論模型選什麼都不會壞」。
- **硬約束由機制強制，策略交給模型。** 模型只在機制允許的範圍內判斷。
- **狀態一律寫檔不寫記憶體。** v1 只支援 session 存活期間，但檔案落地讓 v2 的
  daemon 只需新增讀取者，也是崩潰復原的唯一依據。

## 七、安全，要知道但 v1 不解

`bg_start` 執行**任意 shell 指令、detached、無確認**，而且**活過 agent 被中止**。
中止 agent 不會中止它的背景工作。這既是功能價值也是風險，同源。

v1 靠 `bg_cancel`（殺整棵進程樹）、`session_start` 對帳、磁碟稽核軌跡兜住。
**沒有 allowlist、沒有確認提示。** 若要把這個 bridge 接到不受信任的 prompt 來源，
先加。
