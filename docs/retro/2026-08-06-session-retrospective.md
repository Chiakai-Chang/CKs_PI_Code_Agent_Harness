## 二、做錯的事,依代價排序

**1. 沒讀自己寫過的筆記就動工 —— 代價:一整天。**
推進器做在 `turn_end`、退場計數器數注入次數。這兩個缺陷,
`docs/superpowers/pi-until-done-learnings/02-*.md` 早就白紙黑字寫過,
而 `reference/pi-until-done` 有現成實作。
**五次真實 run、兩小時的量測,「實測發現」的就是那兩行。**

**2. 登記表建在錯的清單上 —— 使用者當場糾正。**
我照 `external-manifest.json` 建,而 README 才是擁有者實際讀到、記得的清單。
從登記資料反推關聯本身就是偏誤來源。改用三份清單交叉比對後,第一次跑就抓到四處漂移 ——
包括**有答案的那個 repo(`pi-until-done`)根本不在 README 裡**。

**3. 門檻憑感覺定 —— 第一次真實 run 就被繞過。**
階段閘的退場門檻定 2 次。模型寧可吸收兩次擋阻再繼續,因為認領只要一次寫入。
**門檻該由「哪一邊比較便宜」決定,不是「感覺合理」。**

**4. 破壞測試的 fixture 無法區分 —— 今天兩次。**
`research-depth` 用 `sed -i` 當案例(抽取器根本不認它);
`phase-gate` 的「兩個 open task」少了一個 PENDING,拿掉守衛結果一樣。
**兩次都是「破壞了、測試卻綠」才發現的。**

**5. commit 訊息的數字先於事實 —— 寫了「五種破壞」而只有四條測試。**
補上第五條讓數字為真,不是把數字改小。

**6. 移開誘餌的方式錯了 —— 我自己造成 run 3 報廢。**
把佇列改名成 `02_Task_Queue_PARKED` 留在 repo 裡,模型找到它、寫了 9 次、全被擋、整場結束。
**移開誘餌是移出專案,不是改名。**
