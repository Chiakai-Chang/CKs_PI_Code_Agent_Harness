# 復盤：2026-07-28 分層技能註冊

**日期**：2026-07-28
**觸發**：使用者對「一直砍技能」提出質疑——「那用原始 pi 不就好了？本專案還有意義嗎？」
**方法**：先量測再設計。用真實 session 歷史決定核心集、用真實 Pi 內的探針擴充驗證效果、用真實本機模型做觸發測試。

---

## 一、使用者的質疑是對的，而且我原本的方向錯了

前兩輪我一直建議「還可以再砍」。把成本歸屬攤開後才看清楚：

| 項目 | tokens/輪 | 佔比 |
| :--- | ---: | ---: |
| 技能索引 | 13,809 | 58% |
| AGENTS.md | 3,738 | 16% |
| CLAUDE.md | 1,393 | 6% |
| pi 原生 + 工具 | 4,556 | 19% |

**9 個 bridge、10 個 `web_*` 工具、pre-bash-guard、containment guard、loop guard、compaction 續接、namespace 隔離、restore/uninstall——2,453 行程式碼，每輪 prompt 成本接近 0。**

也就是說：**砍技能省的錢，和本專案的價值來源完全不重疊。** 「用原始 pi 就好」的推論不成立，但「一直砍」的方向確實會傷到專案——只是傷的不是成本，是可發現性。

## 二、量測推翻了看起來比較安全的方案

| 方案 | 每輪成本 | 省下 |
| :--- | ---: | ---: |
| 現狀（145 全原生註冊） | ~13,809 tok | — |
| 描述截短至 150 字 | ~11,431 tok | 2,378 |
| 描述截短至 100 字 | ~10,237 tok | 3,572 |
| **核心原生 + 長尾名稱目錄** | **~6,217 tok** | **7,592** |

我原本想提「截短描述」當作低風險替代方案。**數字打臉**：每個技能的固定開銷（XML 標籤 + 絕對路徑 + 名稱）約 213 chars，而描述中位數只有 168 chars。

> **只要一個技能還被原生註冊，最低就是 ~213 chars，截描述動不到它。**

光是 `<location>` 絕對路徑就吃掉 3,024 tok，而且由引擎控制、改不了。

## 三、最重要的發現：技能一次都沒被載入過

原本打算用「實際用量」決定核心集。第一版量測說 55/145（37.9%）用過。**但那個量測是錯的**——它比對「路徑字串出現在 session 任何位置」，於是 `bash` 工具列目錄的輸出也被算成「用過」。

收緊成「必須是 `read` 工具呼叫的參數」之後：

```
skills registered:            124
loaded via a read tool call:  0
```

再確認不是走 `/skill:` 斜線指令載入的（掃 165 則使用者訊息，零次）。

**56 個 session、2,315 個 assistant 回合，沒有任何一個已註冊技能被真正載入過。** 13,809 tok/輪買到的是零。

這把問題重新定義了：**這不是「目錄太大」的問題，是「技能機制對這個模型完全不啟動」的問題。** 也直接證實 CLAUDE.md 那句「不被觸發的能力等同不存在」——本 harness 自己就踩在上面。

因此核心集不能用「用量」推導（用量是零），改用**意圖**推導：AGENTS.md §10 路由表與 CLAUDE.md 方法論優先段落點名的那些技能。20 個核心原生註冊，104 個進目錄。

## 四、實測結果

Pi 內探針擴充（排在注入鏈最尾端才看得到完整 prompt）：

```
修改前：systemPrompt 95,559 chars
修改後：systemPrompt 49,485 chars     (catalog: true, skills-block: true)
```

**降 46,074 chars（約 11,518 tokens/輪），124 個技能全部仍可發現。**

## 五、觸發測試：一半成功，而且是實測出來的

規格書把「模型是否真的會用目錄」列為**唯一沒有證據支撐的假設**。實測（本機模型、真 Pi）：

第一次：
```
read  pi-config/skill-catalog.json      <- 找到並打開了目錄
web_search "agent-architecture-audit …"  <- 然後跑去搜網路
web_search "agent-architecture-audit …"
```

**機制的難的那一半成立了**（模型會找到目錄），但它拿著剛讀到的本地 `path` 不用，跑去搜網路。原因不難猜：`stealth-web-bridge` 自己的 promptGuidelines 寫著「You CAN access the internet: call web_search for any task needing current or external information」，那條指令一直在拉它往網路走。

另外它用 `limit: 300` 讀一個 525 行的美化 JSON——**目錄有一半根本不在它讀到的範圍內**。

兩個修正都來自這次觀測，不是推測：
1. `write_catalog()` 改成一行一個技能：525 → 109 行，一次 read 一定讀得完。
2. 目錄注入文字改成明確兩步驟編號，並直說「這些是本機檔案，不要用 web_search 找技能」。

第二次：
```
read  pi-config/skill-catalog.json
web_search …
web_search …
read  external/ecc/skills/agent-architecture-audit/SKILL.md   <- 到了
```

**目錄 → 本地 SKILL.md 的路徑完整走通。** 雜訊般的 web_search 仍在（弱模型本性），但技能確實被載入了。

**誠實的限制**：這次測試我在提示裡**直接點名**了那個技能。所以它證明的是「模型想用某技能時，目錄能把它導到檔案」，**不是**「目錄提升了自主發現率」。後者還沒有證據。

## 六、順手抓到的兩個解析 bug

兩個都會在「模型正在決定要不要載入這個技能」的那一刻給它錯誤資訊：

1. `name: "yes"`（YAML 引號純量）沒去引號，於是永遠對不上核心清單、被靜默降級進目錄。
2. 描述正則在 `re.M` 下用 `$`，把**每一個**多行描述截成第一行。

## 七、收穫

1. **成本歸屬要先做，否則會砍錯地方。** 我連續兩輪建議砍技能，直到把 58% / 19% / 0% 攤開，才看清楚專案價值和 token 成本根本不在同一個地方。使用者的直覺比我的建議準。
2. **看起來安全的折衷方案要量測，不要假設。** 「截短描述」聽起來風險低，實際只省 17%——因為成本在固定開銷而非描述。沒量的話會做一個沒用的功能，還以為自己很穩健。
3. **量測程式本身要驗證。** 第一版用量數字（37.9%）被 `bash` 列目錄的輸出污染，真值是 0%。**差了 55 個技能**。如果照那份數字設計，核心集會塞滿雜訊。
4. **零結果是最有價值的結果。** 「一次都沒被載入」比任何百分比都更能說明問題所在，而且它把題目從「怎麼縮目錄」改成「為什麼機制不啟動」。
5. **注入的指令會互相打架。** `stealth-web-bridge` 那句「有需要外部資訊就呼叫 web_search」把模型從本地檔案拉走。多個 bridge 各自注入指令時，沒人在看它們合起來會不會互相抵消。
6. **把未驗證假設寫進規格，然後真的去驗。** 規格書第 3.4 節明寫「這是唯一沒有證據支撐的一步」，實測就抓到了兩個真實缺陷（limit 300、web_search 干擾）。若照原設計直接上，這兩個都會在使用者身上發生。

## 八、尚未處理

- **自主發現率沒有證據**：觸發測試點名了技能。要驗證真正的自主發現，需要不點名、只描述任務的 A/B，而本機模型每輪 2–15 分鐘，成本高。
- **AGENTS.md 3,738 tok/輪**無條件注入，未分層。
- **技能索引仍有 ~4,343 tok**（20 核心）。若還要再降，該問的是「這 20 個是不是真的都該常駐」，而不是繼續往長尾砍。
