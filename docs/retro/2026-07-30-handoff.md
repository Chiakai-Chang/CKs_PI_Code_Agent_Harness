## 二、確定成立的成果

### 換模型：Qwythos-27B-v1 MTP Q8_0 取代 Fable-Fusion-711

Qwen3.5 與 Qwen3.6 同族 tokenizer，同一組釘死來源產出的 fixture **sha256 完全相同**，
所以這是第一個真正單一變數的模型比較：同 bytes、同引擎 build、同 `--max-tokens`、
各自用卡片指定的 repeat-penalty、Fable 先暖機。

```
15,308 tok  sha 048e990c36d4   Qwythos 24/24   Fable 0/8    Fisher p = 9.5e-08
23,077 tok  sha f41338e59ce8   Qwythos  8/8    Fable 0/8    Fisher p = 1.6e-04
合併                            Qwythos 32/32   Fable 0/16   Fisher p = 4.4e-13
```

15,308 是 harness 真實每輪負載。Qwythos 到 41,129 prompt tokens 都沒有門檻。

### 三個儀器缺陷（每一個都讓失敗變成缺席）

| 缺陷 | 後果 |
|---|---|
| 逾時記成 error | 掉出分母；最可能失敗的回合系統性消失 |
| `max_tokens` 寫死 32768 | 失控回合 25 分鐘一次，整批跑不完 |
| `fetch` 的 undici `headersTimeout` 約 300 秒改不掉 | 41k prompt 時 3/6 請求「失敗」但 server 算完了，下一次命中暖快取，時間數字被反轉 |

第三個最陰險：`AbortSignal.timeout` **管不到** undici 內部那個逾時，Node 也沒有公開介面能改。
已改用 `node:http`，其 `setTimeout` 是 idle-socket 期限；對「非串流、全程靜默、最後才回 headers」
這種流量形態就等於整體期限。

### 兩個 parser／guard 漏洞（同一個洞的第三、第四次）

* Laguna 的 `<tool_call>NAME<arg_key>k</arg_key><arg_value>v</arg_value></tool_call>` 回傳 null
* `File read. Stopping as instructed.`（無檔名、無「I have」）被當成普通 no-call

兩者都是：template 教一種格式 → parser 沒有對應分支 → 退化的回合把它當文字洩漏 →
**無 strike、無糾正、靜默卡死**。負向對照也一起寫了（`the file read failed` 不能誤判）。

### 可重建的量測基礎設施

`scripts/make-probe-fixture.py`（20 tests）：從**解析後的 40 字元 commit** 產生 fixture、
寫 sha256 manifest。`--sources rules|neutral` 讓填充物形狀成為可控變數。

## 三、被推翻的東西（重要，不要照著舊結論走）

### 舊的 Fable 階梯退役

`671→12/12、14,095→12/12、16,880→8/8、20,100→8/8、23,083→6/8、26,052→6/8` —— **不能再引用**。

1. 它是用會把逾時丟出分母的儀器量的（今天 16 次裡 7 次逾時）
2. 光是計數方式解釋不了：舊基線 14,095 是 12/12，今天同尺寸同 bytes **0/8**

連帶：2026-07-29 交接檔第 69 行「約 9% 的回合會拒絕或捏造」**是低估**，
「這個比率在 671 到 26,052 tokens 之間量不出差別」建立在被污染的分母上。
**昨天那次撤回本身仍然正確**（那些配置比較確實無效），倒掉的是基線。

### 兩個候選模型排除，理由不同

* **Laguna-S-2.1**：連專為此硬體調校、tool-eval 贏官方 29% 的社群版，工具呼叫接受率也只有
  70.18%，官方 Q4_K_M 只有 54.39%；我們實測 4/12。且 lemonade build 不認 `laguna`，逼著同時換引擎。
* **MiMo-V2.5**：卡片自陳有 runaway CoT「with no progress or tool calls」，且在 Q8_0 上重現 ——
  正是我們在治的病。另需自 build ROCmFPX fork。

### 機制問題：兩次都答不出來，已停手

假設「harness 注入的規則與 user 請求競爭注意力」（來自 26k 那次唯一失敗

**兩個模型都沒有可用的工作區間**。要研究它必須先造出一個能穩定產生部分失敗的設定。

## 四、機器狀態（重開機後要重建）

### 1. 先驗 64/64 切分，這是這次最優先的事

llama-server 隨重開機消失，用模型目錄裡的 Qwythos 啟動腳本重開。**啟動後立刻對三行**：

```
load_tensors: offloaded 66/66 layers to GPU          <- 最關鍵
load_tensors: ROCm0 model buffer size = 26402.70 MiB
llama_kv_cache: size = 16384.00 MiB (262144 cells, 16 layers, 1/1 seqs)
```

第一行是無聲失敗的所在：VRAM 不夠時 llama.cpp 會**靜默**把部分層丟回 CPU，
速度掉一大截但不報錯（跟漏 `--chat-template-file` 同一類）。

64 GiB 的預算（總計約 46.9 GiB，剩約 18 GiB）：

```
model 26,402.70 + KV 16,384.00 + draft KV 1,024.00 + recurrent 1,047.38 + compute 488.00
= 45,346.08 MiB，加上 [spec] MTP context 1,512 MiB ≈ 46.9 GiB
```

以實測 64 KiB/token 外推（**係數是實測，總額是外推**）：262144 寬鬆、393216 可行、
524288 幾乎貼滿不建議、1048576 放不下。

### 2. 其餘啟動與量測前置

* **等 `/v1/chat/completions` 回 200 再開始**。載入中 `/props` 就會回應但那支回 503，
  曾有一整批數據因此作廢。
* `/props` 要對兩件事：`model_path` 是 Qwythos 那個 GGUF；`chat_template` 第一行是
  `{%- set image_count = namespace(value=0) %}`（Qwythos 自帶，161 行）。
  **若出現 `qwen3.6-froggeric-v21.3` 就是套錯 template** —— 那是 Fable 用的。
* **量測前先暖機**（灌 10 個短請求）。暖機狀態仍是未量化的變數，報告一定要註明。
* Qwythos 載入約 **29 秒**（Laguna 要 1 分 24 秒），實驗迭代成本低很多。

### 3. 本機設定（都在 `.gitignore`，不進 repo）

`pi-config/models.json` 與 `pi-config/settings.json` 現在**都是** `qwythos-27b`
（先前兩者不一致，一個指 Q4_K_M、一個只宣告 Q6_K，已修）。
`contextWindow 262144`、`maxTokens 16384`。

**這個 repo 不預設任何模型，也不該被改成預設任何模型。** 換模型是每台機器自己的事。

## 六、量測紀律（累積版）

1. **先量目標的真實值，再設計 fixture。**
2. **釘死量測輸入**（`git show <resolved-commit>:`），manifest 不能寫 `HEAD`。
3. **fixture 由 bytes 釘死，token 數是 (fixture, 模型) 配對的性質。** 跨模型比 sha256。
4. **兩邊都必須落在非地板、也非天花板區。** 同時觸底與同時觸頂一樣沒有資訊量 —— 這次踩到三遍。
5. **差異要先過統計檢定再當訊號。**
6. **結論本身要通過合理性檢查。**
7. 健康檢查要打真正要用的端點。
8. **每個模型跑兩組取樣**：卡片指定的，以及共同基準。釘死取樣會把模型推出調校區間。
9. **量測時關掉所有 server 端狀態機制**（`--cache-ram 0`、`--ctx-checkpoints 0`）。
10. **失敗必須留在分母裡。** 逾時、撞上限都是 fail 不是 error ——
    儀器把失敗變成缺席，而缺席看起來就像成功。這一條今天用三種形式各咬了一次。
11. **借來的數字不算證據。** fixture 大小、MTP acceptance，兩次都不成立。
