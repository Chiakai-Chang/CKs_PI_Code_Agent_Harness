# 復盤:一天之內,一個死掉的守衛、一個誤擋、一個永遠不會響的提醒(2026-08-11)

九個真實 run、四個任務(T-A1、T-A2、T-A3、T-A6),全部走 Path A 由人核可。
這份是「學到什麼」,不是「做了什麼」——做了什麼在 PROGRESS.md。

---

## 一、三個缺陷,同一個形狀

| 缺陷 | 綠燈的測試怎麼漏掉它 |
|---|---|
| 驗收物守衛從未生效(`_cwd` 不在 scope) | 單元測試呼叫**純函式**(它是對的);接線測試斷言**原始碼字串**含有那個呼叫(它確實含有) |
| containment 誤擋只讀指令(`data/*.json` → `/*.json`) | 沒有任何測試餵過「相對路徑裡含斜線」的形狀 |
| 目標重述在 C.A.S.E. 專案永遠不會響 | 測試都在測**觸發之後**的行為,沒有人問「它在真實提示下會不會被武裝」 |

**共同點:測的是零件,不是那條路。** 三個都要真實 run 才會現形,而三個都在同一天現形,
因為那天終於有一個乾淨的、路徑不含 harness 名稱的場地可以跑。

留下的規則(已寫進 CLAUDE.md):
> **守衛「接好了」的定義是它的公開入口會拒絕**,不是輔助函式回傳正確清單,
> 也不是呼叫出現在原始碼裡。

## 二、寬容的 catch 會吞掉致命的錯

```ts
try { missing = missingDodArtifacts(taskDir, cwd, existsSync); }
catch { missing = []; }        // 「recipe 讀不到就 fail open」
```

這個 catch 是為「recipe 格式不對不要卡住狀態機」寫的,結果吞掉的是 `ReferenceError`。
**為某一種失敗寫的寬容,吞掉了另一種完全不同的失敗**,而且沒有任何跡象。

修的時候還踩了第二次:只把 `evaluate()` 的識別字接上,**`checkTransition()` 那一層
一模一樣地壞著** —— 一個缺陷跨兩個 frame,修一半看起來就像修好了。

## 三、fixture 分不出「有效」與「不存在」

三次:

1. 替換 fixture 用了 `Task_001`,不符 `^Task_(\d+)_` → `taskDirOf()` 回 null →
   **每一個** status 寫入都被放行,包括字串 `bogus`。測試紅了,但**紅的理由是錯的**。
2. 校準值的出貨值與程式碼 fallback **是同一個數字**,只驗出貨情境的測試
   分不出「讀了 config」與「根本沒讀」。
3. 第一版校準測試驗的是 `listingCap()` 這個輔助函式 —— 把呼叫點改回 `slice(0, 5)`,
   **十條全綠**。加了可注入的 root、改從 `check()` 的拒絕文字驗,才會紅。

規則:**當 fixture 讓守衛「放行」時,先確認它有能力拒絕任何東西。**
以及:**分不出兩種世界的測試,不是測試。**

## 四、誤擋不花掉結果,它花掉呼叫數

run 5 的 containment 誤擋擋了兩次只讀指令。**最終 DoD 仍然 11/11** ——
模型沒有停下,它繞路:寫一個暫存腳本再執行。唯一的痕跡是 **33 次呼叫 vs 23**、
**4 分鐘 vs 2.5**。

如果只看通過率,這個缺陷永遠不會被發現。

## 五、「一句話」不是機制

CLAIM 閘被加上「**剛才那次寫入的內容沒有被保存**」之後:

* run 4:模型讀到,認領後**重寫了報告**。看起來這句話解決了問題。
* run 7:模型讀到同一句話,**還是直接去寫 REVIEW** —— 是第二道守衛(驗收物守衛)
  把它擋回來的,它才去 `read` 檔案、拿到 ENOENT、重寫。

**n=1 的成功不能證明一句話有效。** 真正把結果固定下來的是那個會拒絕的守衛。

## 六、任務太簡單,量到的就是任務

前八個 run 連續 11/11,而那證明的是**任務太簡單**,不是機制有效。
Task_001 認領之後只剩 6 個工具結果,而重述門檻是 12 —— 機制**結構上不可能響**。

**長度不能來自更多資料。** 40 個檔案會被一個 for-loop 三步收掉(舊疤)。
Task_002 的長度來自**不可批次的步驟**:驗證器一次只報一個違規,下一個要修什麼,
只有跑過才知道。結果:57 次呼叫 / 47 個回合,重述終於送達兩次。

**而且我在跑之前就把失敗條件寫死**:如果模型自己讀 `check.py` 推出全部違規、一次改完,
那是設計輸了,不是再加規則。它沒有這麼做。

## 七、我自己違反了「fixture 必須可重建」

復盤時才發現:**今天所有數字**(11/11 五次、9/9、57 vs 23)都由兩個放在
`/tmp` 與 session 暫存區的腳本產生,跑在一顆**曾經在工作中途斷線過**的抽取式磁碟上的
任務包上,而 PROGRESS.md 引用它們當證據。

這條規則本 repo 早就寫過(`probe-fixtures-must-be-rebuildable`),我整天都在違反。
已修:[experiments/pitasklab/](../../experiments/pitasklab/README.md) —— 重建腳本、
兩個評分器、驗證器與任務包都進版控,重建出的場地未解 2/9、套上答案 `ALL OK`,
與實際跑的場地行為一致。Task_002 位元一致,Task_001 是答案一致、位元不同(已寫明)。

## 八、帳本會過時,而查證前提是最划算的一步

三個任務,三次前提被推翻:

* T-A2:「`MAX_REFUSAL_TURNS` 硬編在程式碼裡」—— 覆蓋路徑早就有了,
  真正的問題是**全域檔裡沒有那個 key**,所以 snapshot 永遠是空的

* T-A6:「連續五個 11/11」—— 那是任務的分數,不是機制的分數

**每一次都是動手前五分鐘查出來的,每一次都改變了要做什麼。**
