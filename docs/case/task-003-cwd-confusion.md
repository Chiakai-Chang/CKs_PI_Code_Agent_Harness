## 問題

cwd 混淆是 2026-08-06 量到的最大單一失敗來源:五次 advancer run 有兩次被它整場吃掉
(擋阻 11 次與 72 次,狀態一次都沒離開 `PENDING`),另有一次 Task_016 的 run 想把報告
寫進本 repo。每一次都是同一個形狀 —— 相對路徑被解析到 harness 安裝位置,而不是這次的工作目錄。

**成因不神祕,是訊噪比。** Pi 送出的系統提示裡 harness 的絕對路徑出現 **28 次**,
幾乎都是技能的 `<location>`;工作目錄出現 **1 次**。

## 修法,以及為什麼不是「加更多警告」

既有的 containment 守衛**早就擋了、也早就寫了 cwd** —— 而模型在一次 run 裡重試了 **9 次**。

這正是 Task_015/016 量出的中心結論:**擋阻移除錯的路,不供給對的路。**
所以擋阻理由現在附上**把同一個路徑改寫到工作目錄後的版本**,可直接複製,
並說明那個錯路徑為什麼看起來是對的。

`pi-extensions/yes-hooks-bridge/harness-root.ts` 匯出 `harnessRootHint(target, cwd, harnessRoot)`。

**刻意做窄**:與 harness 無關的目錄**不給建議**(那要用猜的,而會猜的守衛沒人信);
在 harness 內工作不算混淆;不知道 harness root 時退回原樣。

## 解除:兩個破壞都重現過,都會紅

**破壞一** 需要兩件事,而不是一件。加了 negation-removal 運算子之後那一行才有變異點
(原本只有 40/42/46 有站點,第 45 行一個都沒有)—— **但光有運算子不夠**:
把整行刪掉重現一次,12 條測試仍然全綠。

原因是 fixture 無法區分,而且是算術上的巧合:所有「無關路徑」的測資都**比 harness 根目錄短**,
少了前置判斷之後 `t.slice(h.length + 1)` 得到空字串,被下一行 `if (!rest) return null` 意外接住。
補一條**比 harness 根目錄長**的無關路徑,重現破壞 → 紅。

**破壞二** 的修法是搬程式碼,不是把斷言寫緊。`index.ts` 需要 Pi runtime,
那裡只能寫字串斷言,而字串斷言擋不住把行為換成 `null`。
理由字串改由 `containmentRefusal()` 純函式產生,放進已被行為測試驅動、
且已納入變異掃描的 `harness-root.ts`;`index.ts` 只呼叫、不排版。
這是本 repo 既有的 pure-logic/runtime 分離慣例(取自 auto-pi 的 `workflow-gate-logic.ts`)。

窮舉掃描:**10/10 全殺**。

## 這一項最後留下的教訓

**驗收要重現原本那個破壞,不是驗工具有沒有覆蓋到那一行。**
新運算子讓第 45 行「有站點了」,而破壞仍然活著 —— 兩者差了一個 fixture。
**「工具能碰到」與「測試能區分」是兩件事。**
