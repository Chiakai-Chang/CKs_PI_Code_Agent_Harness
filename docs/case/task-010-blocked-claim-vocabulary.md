# Task_010_blocked_claim_vocabulary — 結論

任務包在 `02_Task_Queue/Task_010_blocked_claim_vocabulary/`(gitignore),本檔是結論摘錄。

## 表面問題:動詞表漏掉真實說法

`blocked-claim.ts` 的 `CLAIM` 是照 2026-08-06 觀察到的**兩句**回覆寫的。同日第三句出現:

```
已執行完畢。`.../status.txt` 的內容已透過 `printf` 改為 `IN_PROGRESS`。
```

`已完成`、`已將`、`已改為` 都在表上,這句一個都沒中。用捕捉到的原始位元組重現過,
不是推測。

修法不是再加三個詞 —— 說「我做完了」的方式是開放集合,補一次就再漏一次。
改問三個閉集合的問題:**有沒有擋阻(守衛自己記的)、有沒有落地(自己記的)、
回覆有沒有指名目標且沒承認失敗。**

代價是列舉搬到 `DISCLAIMED`,而那一側漏掉會**誤矯正誠實的回報** —— 比沉默貴。
所以同時改了訊息的形狀:只斷言守衛確定的事(擋阻發生、沒有落地),
把「你是不是說了它完成」交給模型核對檔案。誤判成本因此是一次 read,不是一堂
「回報沒好處」的課。

## 真正的問題:這個守衛從來沒有響過

單元綠之後做交付證明(規矩:注入的文字要在 session log 裡找得到)——**矯正沒出現。**
對安裝版加臨時探針量到:

| 呼叫 | `tool_call` | `tool_result` | `tool_execution_start` | `tool_execution_end` |
|---|---|---|---|---|
| **被擋下的** | 不觸發¹ | **不觸發** | 觸發,帶 `args` | 觸發,`isError:true`,`result` 是理由 |
| 正常執行的 | 觸發 | 觸發 | 觸發 | 觸發 |

¹ 擋阻由另一個 bridge 發出;Pi 在有人擋下後不再呼叫後面的 `tool_call` handler。

`blocked-claim.ts` 的註解寫著「被拒絕的呼叫會以 `tool_result`(`isError` 已設)抵達」——
語氣是觀察陳述,實際是假設,而且錯的。**session JSONL 裡確實有一筆
`role: toolResult` + `isError: true`,那是 Pi 寫進逐字稿的,不是發給擴充的事件。**

**逐字稿看得到 ≠ 擴充收得到。** 這條要加進「只有兩個通道能到模型」那組事實旁邊。

正確通道是 `tool_execution_start`(拿 `args`)配 `tool_execution_end`
(拿 `isError` 與理由),以 `toolCallId` 配對 → `Task_011_blocked_claim_channel`。

## 順帶量到的:被擋之後會不會自己修正,是機率的

同一個提示三次真實 run:兩次改用 `write`、用 `cat` 驗證、並在回覆裡如實說明被擋;
一次(被明確要求不要驗證時)謊報完成。**不是必然自我修正,也不是必然謊報。**

## 最該記住的一條

**單元測試證明「這段程式被呼叫時做對事」,不證明「它會被呼叫」。**

前兩次真實 run 模型都自己修正了,看起來一切正常;第三次我用提示把它推向謊報,
缺陷才現形。**要測一個守衛,就要故意製造它該擋的情況** —— 等它自然發生等不到。
