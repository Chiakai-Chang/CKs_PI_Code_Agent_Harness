# Task_005_research_depth_bash — 結論

任務包在 `02_Task_Queue/Task_005_research_depth_bash/`(gitignore),本檔是結論摘錄。

## 修了什麼

`research-depth.ts` 的兩個閘先前只認 `write` / `edit`,於是:

* **產出閘**(第 13 次搜尋時仍 0 次寫入就擋)對「用 bash 寫過檔」的 run 誤擋 ——
  它一直在懲罰已經做完的工作。
* **引用閘**(≥800 字或累計 ≥2500 字、開過 ≥2 頁卻 0 個網址)**根本沒看到用 heredoc
  寫出去的報告**。而引用閘是這個 harness 裡唯一被實測證明會改變行為的守衛:
  檔案內的網址從 0/0/0 變成 10/15/0。

不是假設。乾淨重測的逐字稿裡,模型的交付就是 `cat > ".../output.md" << 'EOF'`。

現在:非 scratch 的每個 bash 寫入目標計一次 `writes`;內容抽得到(heredoc 主體、
`printf`/`echo` 字面)就併入引用閘;抽不到就計數但不判,並累加 `uncheckedWrites`。

## 三個只有規劃復盤才抓得到的設計錯誤

**一、不需要第三份抽取器。** recipe 原本要求「三份平權」。但 `research-depth.ts` 與
`bash-containment.ts` 同屬 `yes-hooks-bridge`,直接 import 即可 —— 跨 bridge 才需要複製。

**二、把 scratch 寫入算進產出閘,等於親手弱化它。** `echo x > /tmp/f` 就能滿足
「留下點東西」。沒有任何測試會為此變紅,它只會安靜地讓守衛失效。

**三、引用閘的部分覆蓋在這裡是對的,和 Task_004 相反。** Task_004 拒絕解析 bash 內容,
因為協定本來就要求用 `write` 改 status,有明確的替代路徑;這裡沒有 ——
CASE 之外用 bash 寫檔是完全正常的工作,拒絕解析等於放棄整條路徑。

**判準是「有沒有被規定的替代做法」,不是「解析得完不完整」。**

## 部分覆蓋要看得見才誠實

`uncheckedWrites` 不擋任何東西。它的價值是讓「這個守衛沒看到多少東西」有一個數字 ——
沒有它,partial coverage 會被讀成 full coverage。

它只出現在 `ctx.ui.notify`,也就是只有操作者看得到、模型收不到。**這是刻意的**:
它是覆蓋率指標,不是給模型的指令。

## 已知缺口

`sed -i` / `tee -a` / `dd of=` 對 `writeTargets` 完全不可見。本任務第一版測試用 `sed -i`
當「抽不到內容」的案例,結果斷言了一個不可能發生的計數,**因為與待測行為無關的理由而失敗**。
補這個缺口要同步改三處與平權測試,是獨立任務。

Task_004 的 retro 已經寫下「修好一個洞之後,要問這個形狀還在哪裡」,而我在同一天又重蹈一次。
**寫下教訓與執行教訓是兩件事。**

那個掃描只要一行 `grep -n 'WRITE_TOOLS\|=== "write"' pi-extensions/*/*.ts`,
代價是引用閘 —— 唯一被證明有效的守衛 —— 有一整天的繞道。三次之後,它應該成為一個檢查:
掃 `pi-extensions/**/*.ts`,凡是以工具名稱集合為條件的分支,同檔沒有 `bash` 分支就報告。
