## 三個結論

### 一、`search-first` 是 0/31。不要為它蓋閘。

T-A8 是因為 run 10 的「搜尋、搜尋、才寫 `task_plan.md`」而立的。
**在 31 個真實 session 裡,「先寫了計畫但寫在搜尋之後」一次都沒發生過** ——
因為幾乎沒有人寫過計畫。run 10 那個順序不是常見的壞,它是**罕見的好**:
它至少寫了。

如果照原訂計畫加一個 `tool_call` 閘去強制順序,那會是**為一個沒有觀察到的失效模式
付出代價**,而這個 repo 已經知道閘的代價:引用閘把「檔案裡的 URL」從 0 拉到 10 的
同一個 run 裡,把捏造的 URL 從 0 拉到 4。

### 二、真正的模式是「長 run 完全沒有計畫」

20 次呼叫以上的 12 個 session,**10 個從頭到尾沒有任何計畫檔**。
其中有 150、240、**865** 次工具呼叫的 run。

### 三、但這是**修好之前**的基線,所以它不能拿來說「建議沒用」

兩個時間點必須寫進來,否則這個數字會被誤讀:

* `research-task-routing` 這個技能**2026-08-05 才存在**(commit `2be4453`)。
  12 個長 session 裡有 9 個比它更早 —— 那些 run 從來沒有被建議過要規劃。
* **整個語料都早於今天的名字修正。** 在 `cd2ecf8` 之前,每一條路由都叫模型
  載入 `planning-with-files`,而註冊的名字是 `pi-planning-with-files` ——
  **載入必定 ENOENT**。就算建議送到了,那條路也是斷的。

所以這 93.5% 量到的是**一個規劃入口壞掉的 harness**,不是「模型不聽建議」。

* 目前唯一的修後資料點是 run 10:32 次呼叫,計畫寫在第 6 次 —— **有計畫**。n=1。

是零。**一次觀察足以提出問題,不足以定義問題。**
今天第四次:帳本寫下的理由,在動手前查證都會變。
