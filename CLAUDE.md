## 🧪 Testing & Verification Commands
* Run tests (zero-dependency, stdlib unittest): `python -m unittest discover -s tests`
* Verify bridge health (entry points exist, manifest vs package.json cross-check, **and whether the installed copies Pi loads still match the repo**): `python scripts/verify-bridges.py`. The drift check needs a machine with Pi installed — in CI it prints SKIP and checks nothing, so run it locally before believing a bridge fix is live.
* Validate pi-config files (schema, anti-patterns, secret detection): `python scripts/validate-config.py`
* Audit the combined injected prompt across bridges (absolutist scope claims, shared trigger vocabulary, total budget): `python scripts/check-prompt-conflicts.py`
* Build a pinned, reproducible fixture for the probe scripts (sizes against whichever model is being served; records sha256 so a rebuild proves the sources have not moved): `python scripts/make-probe-fixture.py --out <dir> --sources rules|neutral --tokens N [--url http://127.0.0.1:8080]`
* Mutate the guards mechanically and require the tests to notice (slow — needs node; NOT in CI): `python scripts/check-guard-mutations.py [--only <module>] [--all]`. Survivors must be named in `scripts/guard-mutation-allowlist.json` with an argument for why no test can tell the difference, or the run fails.
* Report run-to-run variance and the sample size a comparison needs (`n ≳ (sd/(Δ/2))²`, from metaharness ADR-138): `python scripts/measure-advancer.py --variance <results.json...> --delta N`. It groups by the configuration recorded with each run and **refuses to pool runs whose configuration is unknown** — pooling two experiments is the mistake it exists to prevent.
* Measure whether the C.A.S.E. loop drives a task to completion, on real Pi runs (slow — runs the local model; NOT in CI): `python scripts/measure-advancer.py --runs 3 --prompt baseline|research`. Run `--self-check` first: it refuses to measure unless its counters reproduce a fixture built from a captured session.
* Report how the request-shape router classified real session history (fixtures excluded): `python scripts/report-task-shapes.py --from-prompts`. Measured 2026-08-09: 106 real prompts, 18 multi-step (17%), 14 distinct.
* **Read one real session properly** (fast, no model): `python scripts/mine-session.py --latest [--full]`, or pass a workspace substring. Prints the fixed checklist that every finding on 2026-08-09/10 came from — turn and call counts, batching, which injections reached the model, which guard refused and how often, whether consecutive refusals repeat verbatim, whether the model read the files it was also injected (an attribution confound), and the tool sequence. **Controlling variables is only needed to measure an effect, not to find a defect** — so prefer batching changes and mining one session over an A/B, which cost seven runs and produced no conclusion.
* Measure whether restating the goal mid-run keeps a run on target when its own workspace pulls it off (slow — runs the local model; NOT in CI): `python scripts/measure-drift.py --runs 3 [--arm on|off|both]`. A/Bs `enableGoalRestate` alone and scores two independent axes on disk — `owners_found` (how much of what was asked for reached the deliverable) and `baited_files` (how much of what was NOT asked for got done). `--score <dir>` re-scores a workspace without running anything.
* Measure whether mechanisms actually fire, without naming them (slow — runs the local model; NOT in CI): `python scripts/measure-triggers.py [--only ID] [--repeats N]`
* Measure whether the local model still emits native tool calls under load (slow — runs the local model; NOT in CI): `node scripts/probe-tool-calls.mjs --system <pinned file> --tools 13 --repeats 6`. The system prompt must be a **pinned** file (`git show HEAD:…`), never a live repo doc — editing the doc changes the measurement.
* Measure whether a retry recovers after the model fabricates a completed action (slow — runs the local model; NOT in CI; no results yet as of 2026-07-29): `node scripts/probe-retry-recovery.mjs <pinned file> [n]`
* Measure this machine's usable context and write the gitignored local override (slow — runs the local model and the `pi` binary; NOT in CI): `python scripts/calibrate-context.py [--ladder] [--write]`
* Dump the system prompt Pi actually sends, for prompt-budget work: `PI_HARNESS_DUMP_PROMPT=<file> pi --print "..."` (off unless the variable names a file).

## ✅ Evidence-Based Completion (實測有證據)
**Never claim something is done, fixed, or working without running the actual thing and observing the result.** "Should work", "looks correct", or "the code is right" are not evidence — only observed output is. This is the soul of this repo; violating it is the most serious failure here.

* **Test the real entry path, cold.** Exercise the path a fresh user actually hits — the first-use / server-down / clean-clone state — not the already-warm state you happened to set up. (Scar: `web_search` "worked" only because the backend was started manually first; the cold `spawn sh ENOENT` path was never tested and was broken for every new machine.)
* **"Green on my machine" is not proof.** Environments differ — PATH, gitignored files, OS. Reproduce the target condition before claiming pass. (Scar: a test read the gitignored `pi-config/settings.json`; it passed locally and broke on every fresh CI checkout.)
* **Show the evidence.** When reporting done, quote the actual command and its actual output. If you did not run it, say so plainly — do not imply verification you did not perform.
* **Numbers and claims come from a run at write-time.** Any concrete number or success claim in a report or **commit message** ("N tests pass", "covers X files", "3× faster") must come from an actual run at the moment you write it — never a prediction or memory. Run first, use the real value; if you can't verify it then, don't state a specific number. (Scar: a commit said "125 tests" — the real run was 127.)
* **`pi --print` blocks forever on an inherited stdin.** Measured 2026-08-10: launched from a shell invocation that had just consumed a heredoc, it produced 25 minutes of nothing — exit 124, a 0-byte log, an empty session directory. The identical command with `< /dev/null` answered in seconds. Always redirect stdin when launching Pi non-interactively (`< /dev/null`, or `stdin=subprocess.DEVNULL` in Popen). **A hang and a real zero look identical in results**, and two of these were written off as transient before the difference was probed.
* **Pi runs installed copies, not your repo files.** After editing anything under `pi-extensions/` or `pi-skills/`, run `python scripts/setup.py --mode restore` before testing, or you are measuring the previous version.
* **A green unit test is not delivery.** For anything a bridge injects, prove the text reached the model by finding it in the session log under `~/.pi/agent/sessions/**.jsonl`. (Scar: 11 tests passed while the handler returned a bare content array instead of `{ content: [...] }` — Pi dropped it in silence, and only the log showed the tool result unchanged.)
* **Read your fixture's own paths before believing its result.** Four of five probe runs "worked in the wrong project", and the probe workspaces were under `.../Temp/claude/D--MyProject-CKs-PI-Code-Agent-Harness/...` — the cwd carried the harness name. The owner's real sessions: **228 tool calls, 1 harness touch**. A day of guards, a MECE round and a migration design went to an artifact of the measurement. Compare against real session history before ranking any failure mode; it is one query and it was available the whole time.
* **Report capability at the model–harness CONFIGURATION level, never by model alone** (Harness-Bench, arXiv 2605.27922, 5,194 trajectories). Any percentage-point claim must carry the model, the harness commit and the sample size, or it does not go in a document. Borrowed numbers are the same trap: a published 26.5–54% tool-call gap measured **2.5% of turns / 6% of sessions** here.
* **Three layers, and a change belongs to exactly one.** *Protocol* (C.A.S.E.) may depend on nothing model-specific; *enforcement* (bridges) depends on Pi's event model; *calibration* (thresholds, budgets) depends on the specific model. **A protocol-layer change must be explainable without naming any model** — if the reason is "our local model does X", it belongs in enforcement or calibration. `MAX_REFUSAL_TURNS`, the restatement threshold and the listing cap are calibration currently sitting in enforcement code, where swapping models raises no error and only produces silent unfitness.
* **CI is a feature, not noise.** A red CI that catches a real defect is doing its job; fix the defect, do not dismiss the signal.
* **A guard that never fired is unvalidated, not working.** Green tests prove the code does what you told it to; only a live run that actually meets the condition proves the condition happens. State before measuring what a run would have to *do* to trigger it, then check the runs against that. (Scar: two gates passed 11 tests, survived three deliberate breaks, installed clean — and fired 0 times, because the probe opens a page by its third search.)
* **A guard that removes an option must be paired with something that speaks when the option comes back.** Otherwise the model generalises "not available now" into "not available", and that generalisation is rational — it saw N refusals and zero permissions. (Scar: the phase gate took premature searches from 15 to 0 and real research from 15 to 0 in the same run; the model wrote "web_search 被框架攔截" into its own deliverable and answered from memory.)
* **After a guard fires, diff the numbers it did not target.** A threshold defines the shape of the evasion. (Scar: the citation gate took URLs-in-files from 0 to 10 and fabricated ones from 0 to 4 in the same run, and a per-call size floor was answered by writing smaller.)

## 🔧 Harness-Injected Discipline (了解框架幫你做的事)
This harness runs **bridge extensions** that inject behavioral discipline into every session — they are not your tasks to complete, and you should not restate or acknowledge them as goals:
* **Verifiability block** (planning-with-files-bridge): injected **once per user message**, not per agent turn — this line said "each agent turn" until 2026-08-09 and that was never true. It reinforces the Evidence-Based Completion rules above; treat it as background guardrails, not a checklist item.
* **Compaction survival kit** (compact-continuation-bridge): after Pi compacts context, a continuation message may appear telling you to resume unfinished work. The verbatim-preservation header in that message survived compression — follow its instruction to continue the prior task, but do not treat the message itself as new work.
* **Namespace guard** (skill-namespace-guard): live-detects skill-name collisions at session start; its startup warnings are informational.

## 🔌 Pi Extension Facts (查安裝版，不要查 reference/)
* **Read API contracts from the installed package**: `@earendil-works/pi-coding-agent/dist/core/extensions/types.d.ts` and `@earendil-works/pi-agent-core/dist/types.d.ts`. `reference/oh-my-pi/` is a gitignored 0.73-era fork copy, not what runs. (Scar: its `BeforeAgentStartEventResult` has no `systemPrompt`, which made correct bridge code look like a defect.)
* **Only two channels reach the model**: a `tool_result` handler returning `{ content: [...existing, block] }`, and `before_agent_start` returning `{ systemPrompt }`. `ctx.ui.notify` paints the TUI only; `AgentToolResult.details` is "for logs or UI rendering"; `ToolCallEventResult` is `{ block?, reason? }`; `turn_end` declares no result type, so a finding made there must be queued for a later event.
* **A blocked call emits no `tool_result` event** (measured 2026-08-06 with a probe on the installed bridge). It emits `tool_execution_start` (carries `args`) and `tool_execution_end` (carries `isError` and the refusal text, but **no input** — pair them by `toolCallId`); the later `tool_call` handlers are skipped once someone blocks. A guard wired to `tool_result` to catch refusals is silent in every real session. (Scar: it was, for a day, with 12 unit tests green.)
* **The session JSONL is not the event stream.** It contains a `role: toolResult` record with `isError: true` for a blocked call — written by Pi for the log, never delivered to a handler. Visible in the transcript ≠ received by an extension.
* **`before_agent_start` fires once per USER MESSAGE, not per agent turn.** Its own declaration says "Fired after user submits prompt but before agent loop". Measured 2026-08-09 on session `019fe60f`: one user message, sixteen assistant turns (`Uaaaaaaaaaaaaaaaa`). Everything injected there — the Constitution, the Roadmap, the task-shape routing note, the verifiability block — is stated once and is fifteen turns behind by the end. **Nothing in this harness restates the goal mid-run**, and the protocol's own answer to that (§16 Handoff Capsule) is unimplemented.
* **Assistant turns emit tool calls in BATCHES, so an extension's counter lags what the model has issued.** Session `019fe72a` went 2/4/4/4/4/1/1 for 20 calls; a counter over `tool_result` events reached 12 while the model had already made 14. Any number an extension states back to the model must be phrased as what the extension observed (results received), not what the model did (calls issued). No unit test can find this — fixtures feed results one at a time.
* **`sendMessage` with a `customType` is NOT a user message, so it does not start a new prompt cycle.** The queue advancer moves to the next task with `{ deliverAs: "followUp", triggerTurn: true }`, and session `019fcf32` shows a custom message sitting between two assistant turns **with no user message between**. Consequence: **changing task does not re-fire `before_agent_start`** — the Constitution, the Roadmap and a task's own `role.md` never reappear when the work moves on. Every task in a queue run shares one prompt cycle. A real subagent (`pi --print` child) does get its own, which is why it replaces compaction rather than complementing it — but Pi's own example passes `--no-session`, which destroys the audit trail this repo verifies with; use `--session-dir`.
* **A turn that produced no text is not the end of a reply.** Pi ends a turn whenever the model stops, so a tool-only turn fires `turn_end` with empty text. Per-turn state cleared there is gone before the turn that actually speaks.

## 📚 Prior Art First (先查既有,再動手)
**Before designing any new mechanism, open [docs/prior-art/REGISTER.md](docs/prior-art/REGISTER.md) and find the same capability in a source we already cloned.** Write "adopt / port / skip + why" per candidate into the task's `recipe.md > Input Sources`. Skipping this cost a full day on 2026-08-06: a queue advancer was built on `turn_end` with a counter over injections, and a five-run measurement rediscovered — by experiment — the two facts our own `docs/superpowers/pi-until-done-learnings/02-*.md` already stated in writing (`agent_settled` owns continuation; the spin guard keys on progress signals). `reference/pi-until-done` implements both.
* **Review procedure (three reviews in, this is what works):** (1) **check provenance before content** — is that ADR `Proposed` or `Accepted`, is that strategy doc AI-generated, are those numbers targets or measurements? Both of the highest-value findings so far came from this step, and both were corrections to citations I had already made. (2) Read the docs/index and the two or three items **closest to a problem we currently have**, not the tree. (3) Produce a decision that points at our code — adopt, port, or **a written trigger condition for not adopting now**. "No adoption, and here is what would change that" is a full result, not a failure.
* **A prior-art review audits us as much as the source.** Three of three so far produced a finding about this repo, not the clone: a `Proposed` ADR quoted as a decision, two sources cited in shipped code while the register called them unreviewed, and `01_Roadmap/global_dod.md` sitting unread as an unfilled template whose one real criterion ("all tasks DONE") was the exact fallacy the source warned about. Expect the audit, and check what the source's claim implies about our own files before writing the adopt/reject table.
* **Stop reviewing when the port backlog outgrows the reading.** Each review adds "待移植" rows; none of them help until one is built. After a tier, weigh another source against implementing what the last ones found.
* **Cloned ≠ reviewed; reviewed ≠ remembered.** The register's 審視狀態 column is the difference, and `python scripts/check-prior-art.py` (in CI) keeps README's list, the manifest and the clones on disk from drifting apart.
* **Write down what you rejected and why.** An undocumented rejection gets rebuilt by the next person — the "judge system is the extension layer's job" exclusion in `07-optimization-plan.md` was silently reversed months later by rebuilding a weaker judge.

## 🧭 Methodology-First (方法論優先)
This repo bundles many **methodology skills**; they only add value when invoked at the right moment — otherwise they are unused shells (same lesson as camofox: a capability that is never triggered is as good as absent). **Process skill first (sets the approach), then domain skill (executes).** Before non-trivial work: new/creative work → `brainstorming` then a plan; a bug → `systematic-debugging`; implementing → `test-driven-development`; a complex multi-step task → `planning-with-files`; a decision with trade-offs → `thinking-frameworks` / `mece-autopilot` / `qiushi`. Do not skip the method and dive straight into code. (Full routing: `pi-rules/AGENTS.md` §10.)

## 🚫 Forbidden Anti-Patterns
* **No Marketing/Hyperbole**: Do not use boasting words like "master-class", "revolutionary", or "15+ top repos". Speak plain, objective engineering truths.
* **No Zombie Configs**: Never register mock or empty extension files in `settings.json`. Every registered item must be active and tested.
* **No OS-Specific Hardcoding**: Do not put machine-specific paths (e.g. `C:\Program Files\Git...`) inside shared template configuration files. Use `setup.py` for runtime injection.
* **Shell & Execution**: Pi Coding Agent executes commands natively using `bash` (even on Windows). Ensure all harness configurations, scripts, and commands are strictly compatible with bash syntax rather than CMD/PowerShell.
